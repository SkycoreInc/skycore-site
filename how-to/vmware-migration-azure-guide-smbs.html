Your Comprehensive VMware Migration to Azure Guide: A SkyCore Solutions Blueprint for SMBs

For many small and medium-sized businesses (SMBs) in Montreal and beyond, the challenges of managing aging on-premises VMware infrastructure are all too familiar. High maintenance costs, limited scalability, and complex security updates can stifle growth and consume valuable IT resources. The solution? A strategic move to Microsoft Azure. This comprehensive VMware migration to Azure guide, crafted by SkyCore Solutions, will walk you through the entire process, empowering you to transition your virtual machines to a flexible, secure, and cost-effective cloud environment. By following these steps, you'll leverage Azure Migrate's agentless capabilities to assess, replicate, and migrate your workloads, setting the stage for enhanced agility and operational efficiency.

Prerequisites

  • Active Azure Subscription: Requires an Azure account with Contributor and User Access Administrator roles. These are necessary to create resources and manage permissions.
  • Azure CLI: Latest version of the Azure CLI installed and configured on your workstation.
  • Azure Az PowerShell module: Latest version of the Az PowerShell module installed and configured.
  • VMware vCenter Server: vCenter Server (versions 5.5, 6.0, 6.5, 6.7, 7.0, or 8.0) is required.
  • VMware User Account: A read-only user account for vCenter Server for discovery, and a separate account with specific permissions for agentless replication (VM creation, power on, etc.). Refer to Microsoft Learn documentation for precise permissions.
  • Azure Migrate Appliance Host: At least one Windows Server 2016/2019 VM or physical server (with internet access) in your VMware environment to host the Azure Migrate appliance. This server should have sufficient resources (e.g., 8 GB RAM, 4 vCPUs, 200 GB disk space).
  • Local user account on VMware vCenter Server: With specific permissions for agentless migration (refer to Azure Migrate documentation for details).
  • Estimated Cost: While Azure Migrate itself is a free service, the Azure compute, storage, and networking resources consumed by your migrated VMs will incur charges. We will discuss cost optimization strategies like Azure Hybrid Benefit.

Step 1: Prepare Your Azure Environment

Before initiating any discovery or migration, it's crucial to set up the foundational components in your Azure subscription. This involves creating a dedicated resource group to logically organize your migration assets and an Azure Migrate project, which acts as a central hub for all your migration activities.

First, create an Azure Resource Group:

az group create --name <your-migrate-resource-group> --location eastus
  • --name <your-migrate-resource-group>: Replace with a descriptive name for your resource group, e.g., SkyCoreMigrateRG.
  • --location eastus: Choose an Azure region close to your business or where you want your resources to reside. eastus is a common choice.

Next, create an Azure Migrate project within this resource group:

az migrate project create --resource-group <your-migrate-resource-group> --name <your-migrate-project-name> --location eastus --public-network-access Enabled --scope Subscription --tags Project=VMwareMigration Owner=SkyCoreSolutions
  • --resource-group <your-migrate-resource-group>: Use the name of the resource group you just created.
  • --name <your-migrate-project-name>: Assign a name to your Azure Migrate project, e.g., SkyCoreVMwareProject.
  • --location eastus: Must match the resource group location.
  • --public-network-access Enabled: Enables connectivity from public networks. For SMBs, this is typically fine.
  • --scope Subscription: Specifies the scope for the project.
  • --tags Project=VMwareMigration Owner=SkyCoreSolutions: Best practice for resource organization and cost management.

Portal alternative: Navigate to the Azure portal, search for "Resource groups", click "Create". Provide a name and region. Then search for "Azure Migrate", click "Create project", select your subscription and resource group, and provide a project name and region.

Run this to verify:

az migrate project show --resource-group <your-migrate-resource-group> --name <your-migrate-project-name> --query "provisioningState" -o tsv

This command should return Succeeded.

Pro tip: Ensure the user creating the Azure Migrate project has Contributor and User Access Administrator roles on the subscription. If not, you may encounter permission errors during project creation or appliance registration. You can assign these roles using az role assignment create or via the portal under IAM (Identity and Access Management).

Step 2: Deploy the Azure Migrate Appliance

The Azure Migrate appliance is a crucial component for agentless discovery and migration. It's a lightweight virtual appliance (OVA) that you deploy on your VMware environment. This appliance discovers your VMware VMs, collects configuration and performance data, and securely sends it to your Azure Migrate project.

As per Microsoft's recommended workflow for agentless migration, the deployment of the appliance is primarily a manual download and import into your VMware vCenter environment, followed by configuration via its local web interface. Direct CLI/PowerShell commands for OVA deployment are not available within the Azure Migrate context.

Portal steps:

  1. Navigate to the Azure portal, search for and select "Azure Migrate".
  2. In the Azure Migrate project, under "Migration goals" > "Servers, databases and web apps", select "Discover, assess and migrate".
  3. In "Azure Migrate: Discovery and assessment", click "Discover".
  4. In "Discover servers" > "Are your servers virtualized?", select "Yes, with VMware vSphere hypervisor".
  5. In "Select migration tool", select "Azure Migrate: Discovery and assessment".
  6. Click "Download" to obtain the Azure Migrate appliance OVA file.
  7. Deploy this OVA file on your VMware vCenter Server as a new VM. Power it on and connect to its console to set the password.
  8. Open a browser on any machine that can connect to the appliance VM's IP address and navigate to https://<appliance-ip-address>:44368.
  9. Follow the appliance configuration wizard: accept license terms, set up prerequisites, provide vCenter Server details and the read-only credentials, and register the appliance with your Azure Migrate project using the Azure device code provided in the portal.

SMB Recommendation: The appliance model is highly recommended for SMBs because it simplifies ongoing discovery and keeps your Azure Migrate project updated with the latest inventory and performance data without requiring agents on individual VMs. This agentless approach significantly reduces operational overhead.

Run this to verify: After successful registration, the appliance should appear in your Azure Migrate project. You can check its status via the Azure portal under "Azure Migrate" > "Servers, databases and web apps" > "Discovery and assessment" > "Overview" > "Azure Migrate Appliances".

Step 3: Discover VMware Servers with the Appliance

Once the Azure Migrate appliance is deployed and registered, it begins to discover your VMware virtual machines. This process involves collecting metadata (e.g., VM name, OS, CPU, RAM) and performance data (e.g., CPU utilization, memory utilization, disk IOPS/throughput) from your vCenter Server. This information is crucial for accurate assessment and migration planning.

The initial discovery and ongoing synchronization are managed automatically by the appliance after its configuration. There aren't direct Azure CLI or PowerShell commands to "start discovery" once the appliance is set up; it's an automated process.

Portal steps:

  1. In the Azure portal, navigate to your Azure Migrate project.
  2. Under "Servers, databases and web apps", in the "Discovery and assessment" tile, you should see the number of discovered servers increasing over time (it can take 15-30 minutes for initial server metadata to appear, and up to a day for performance data collection to begin).
  3. Click on the number of discovered servers to view the detailed inventory.

Run this to verify: To ensure discovery is active and data is flowing:

az migrate project show --resource-group <your-migrate-resource-group> --name <your-migrate-project-name> --query "properties.assessmentProperties.lastUpdatedTimestamp" -o tsv

This command shows the timestamp of the last update to assessment properties, indicating active data flow. You should also see your discovered servers listed in the Azure portal.

Common pitfall: Network connectivity issues. Ensure your Azure Migrate appliance has outbound connectivity over HTTPS (port 443) to Azure URLs and to your vCenter Server (port 443) for communication. Firewall rules are a common culprit for failed discovery or registration.

Step 4: Assess VMware VMs for Azure Readiness and Cost

Assessment is a critical planning phase that helps you understand the cloud readiness of your VMware VMs, estimate potential Azure costs, and determine the optimal Azure VM sizes and storage types. This step ensures you right-size your cloud resources and avoid overspending.

For SMBs, we strongly recommend a performance-based assessment. This method analyzes actual CPU, memory, disk IOPS, and throughput usage data collected by the appliance over a specified period. This leads to more accurate recommendations and significant cost savings compared to "as-is" sizing, which simply mirrors your on-premises configuration.

While the detailed assessment configuration is primarily done in the Azure portal, here's how you'd conceptually manage assessment groups (which are a prerequisite for running an assessment):

az migrate group create --resource-group <your-migrate-resource-group> --project-name <your-migrate-project-name> --name <your-assessment-group-name> --description "VMs for production environment"
  • --name <your-assessment-group-name>: A name for your group, e.g., ProdVMsGroup.

Then, add discovered machines to this group. This is typically done in the portal, but conceptual CLI would be:

# (Conceptual) CLI command to add machines to a group - often portal-driven for selection
# az migrate group machine add --resource-group <rg> --project-name <project> --group-name <group> --machines <machine-id1> <machine-id2>

Portal steps for creating a performance-based assessment:

  1. In your Azure Migrate project, under "Discovery and assessment", click "Assess" and then "Azure VM".
  2. In "Assessment type", select "Azure VM".
  3. In "Discovery source", select "Servers discovered from Azure Migrate appliance".
  4. Click "Edit" to review assessment properties:
    • Target location: Choose the Azure region for migration (e.g., eastus).
    • Storage type: Select "Automatic" for performance-based assessment; Azure Migrate will recommend storage based on IOPS and throughput.
    • Savings options (compute): For SMBs, consider "Azure reservations (1 year or 3 year reserved)" for stable workloads, and investigate "Azure Savings Plan (1 year or 3 year savings plan)" for additional flexibility. You can only see estimates for one option at a time in the assessment.
    • Sizing criterion: Select "Performance-based".
    • Performance history: Choose "1 month" or "3 months" to capture typical workload patterns.
    • Percentile utilization: Set to 95th percentile. This balances performance needs with cost efficiency, ignoring peak spikes.
    • Comfort factor: We recommend a Comfort factor of 1.2 to 1.4. This adds a buffer (e.g., 20%-40%) to CPU and memory recommendations to account for seasonal spikes, short performance history, or future growth.
    • VM Series: Exclude any VM series (e.g., A-series) that are not suitable for production workloads. Azure Migrate will suggest based on performance.
    • Offer & Currency: Select your Azure offer type (e.g., Pay-as-you-go, Enterprise Agreement) and billing currency.
  5. Select the group of servers you created earlier or create a new one.
  6. Click "Create assessment".

Run this to verify: Once the assessment is complete (may take a few minutes), you can view its summary in the Azure portal under "Azure Migrate" > "Discovery and assessment". Review the "Azure readiness" and "Cost details" tabs to understand the recommendations and total cost of ownership.

Step 5: Configure Replication for Agentless Migration

With a clear assessment in hand, the next step is to prepare your VMware VMs for migration by setting up continuous, agentless replication to Azure. Azure Migrate's "Migration and modernization" tool orchestrates this process, minimizing downtime during the eventual cutover.

The agentless replication leverages the same Azure Migrate appliance you deployed earlier. There are no direct CLI/PowerShell commands to initiate the setup of replication for individual VMs from the command line within the Azure Migrate context; this is an interactive process primarily managed via the Azure portal.

Portal steps to set up replication:

  1. In your Azure Migrate project, under "Migration goals" > "Servers, databases and web apps", select "Discover, assess and migrate".
  2. In "Azure Migrate: Migration and modernization" tile, click "Replicate".
  3. In "Replicate", on the "Source settings" tab:
    • Are your servers virtualized?: Select "Yes, with VMware vSphere hypervisor".
    • On-premises appliance: Choose the Azure Migrate appliance you previously set up.
    • vCenter Server: Select the vCenter Server from which you want to replicate VMs.
  4. On the "Virtual machines" tab: Select the VMs you wish to replicate based on your assessment plan.
  5. On the "Target settings" tab:
    • Target location: The Azure region where VMs will reside (must match your assessment).
    • Virtual network: Select the target Azure Virtual Network (VNet) and subnet where your VMs will connect post-migration.
    • Resource group: Choose the Azure resource group for the migrated VMs.
    • VM size: Choose to have Azure Migrate recommend based on your assessment or specify manually.
    • OS disk type: Select "Premium SSD" for most SMB production workloads for best performance, or "Standard SSD" for less critical VMs.
    • Availability options: For SMBs, "No infrastructure redundancy required" (single VM) or "Availability set" for basic redundancy of multiple VMs. Availability Zones are for higher-tier redundancy.
    • Azure Hybrid Benefit: Select "Yes" if you have eligible Windows Server or SQL Server licenses with Software Assurance to save significant costs.
  6. Review the settings and click "Replicate".

Run this to verify: You can monitor the replication status in the Azure portal. After starting replication, machines will transition through "Initial replication" and then "Synchronizing" states.

az migrate replication show --resource-group <your-target-resource-group> --name <replicated-machine-name> --query "properties.replicationStatus" -o tsv

Note: The specific resource name for replication depends on how Azure Site Recovery components are exposed within Azure Migrate. In most cases, you would find this information directly in the Azure portal.

Step 6: Run a Test Migration

A test migration is an indispensable step in any VMware migration to Azure guide. It allows you to validate the functionality of your replicated VMs in an isolated Azure environment without affecting your source production workloads. This helps identify and resolve any potential issues (e.g., networking, application compatibility) before the final cutover.

The test migration process involves creating lightweight, non-production Azure VMs from the replicated data. This is typically initiated via the Azure portal.

Portal steps for test migration:

  1. In your Azure Migrate project, navigate to "Servers, databases and web apps" > "Migration and modernization" tile.
  2. Click on "Replicating servers" to view the list of VMs currently replicating.
  3. Right-click the VM you want to test and select "Test migrate".
  4. In "Test migrate", choose the target Azure Virtual Network where the test Azure VM will be created. We recommend selecting an isolated test VNet to prevent network conflicts with your on-premises environment.
  5. Click "Test migrate" to start the operation.
  6. Monitor the job status in the Azure portal. Once complete, navigate to "Virtual machines" and locate your test VM (it will have a suffix like -test).
  7. Connect to the test Azure VM and perform thorough application and network testing.
  8. After testing, return to the "Replicating servers" list, right-click the VM, and select "Clean up test migration" to remove the test Azure VM and its resources.

Run this to verify: After a test migration, you would verify the creation of the test VM using:

az vm list --resource-group <your-target-resource-group> --query "[?contains(name, '-test')].name" -o tsv

This should list any VMs created during a test migration. After cleanup, this list should be empty.

Pro tip: Always perform a test migration for every critical application. This is your dry run. It allows you to identify performance bottlenecks, network misconfigurations, and application dependencies without impacting production. Don't skip this step!

Step 7: Perform the Full Migration (Cutover)

After successful test migrations and addressing any identified issues, you are ready for the final cutover. This is the stage where your VMware VMs are brought online in Azure as production machines, and your on-premises counterparts are shut down.

For SMBs, choosing the right cutover window is crucial to minimize business disruption. Plan for off-peak hours or weekends.

Portal steps for full migration:

  1. Ensure the VM is in a "Synchronizing" state with a low "RPO (Recovery Point Objective)" in the "Replicating servers" list.
  2. For the VM you want to migrate, right-click and select "Migrate".
  3. In "Migrate", select "Shut down virtual machines and perform a planned migration (recommends minimal data loss)". This option ensures the latest data is synced before migration and shuts down the on-premises VM to prevent data divergence.
  4. Click "Migrate" to start the cutover.
  5. Monitor the migration job status. Once complete, navigate to "Virtual machines" in the Azure portal. Your newly migrated VM will appear.
  6. Perform final production tests on the Azure VM.
  7. After successful validation, stop replication for the migrated VM from the "Replicating servers" list. This will clean up the replication artifacts.

Run this to verify: After a successful migration, your VM should be running in Azure.

az vm show --resource-group <your-target-resource-group> --name <your-migrated-vm-name> --query "powerState" -o tsv

This command should return VM running.

Step 8: Post-Migration Optimization and Cleanup

Your VMware migration to Azure guide doesn't end with the cutover. The final phase involves optimizing your new Azure environment for cost and performance, and systematically decommissioning your old on-premises infrastructure. This maximizes the benefits of your cloud investment.

Optimization:

  • Right-sizing: Continuously monitor your Azure VM performance metrics. If an Azure VM is over-provisioned (e.g., CPU utilization consistently low), consider resizing it to a smaller, more cost-effective SKU.
  • Azure Hybrid Benefit: Double-check that Azure Hybrid Benefit is applied to all eligible Windows Server and SQL Server VMs to realize substantial savings.
  • Reserved Instances/Savings Plan: For stable, long-running workloads, purchase Azure Reserved Instances or enroll in an Azure Savings Plan for compute resources based on your assessment.
  • Storage Optimization: Evaluate your disk performance needs. Downgrade from Premium SSD to Standard SSD or even Standard HDD if performance isn't critical, or leverage Azure Blob Storage for archiving.
  • Networking: Implement Network Security Groups (NSGs) for granular traffic control and consider Azure Firewall or Application Gateway for advanced security and load balancing.

Cleanup:

  • Decommission On-Premises VMs: Once you are fully confident in the Azure VMs, power off and eventually delete the corresponding VMware VMs from your vCenter Server.
  • Remove Azure Migrate Appliance: After all migrations are complete, power off and delete the Azure Migrate appliance VM from your VMware environment.
  • Cleanup Azure Migrate Project: If no further migrations are planned, consider deleting the Azure Migrate project and its associated resource group to avoid unnecessary clutter.

Example of resizing an Azure VM:

az vm resize --resource-group <your-target-resource-group> --name <your-migrated-vm-name> --size Standard_D2s_v5
  • --size Standard_D2s_v5: Example new VM size. Always choose a size appropriate for your workload.

Example of deleting the Azure Migrate project (only when completely done):

az migrate project delete --resource-group <your-migrate-resource-group> --name <your-migrate-project-name> --yes
