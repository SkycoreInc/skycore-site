How to Implement Zero Trust Security: A SkyCore Solutions Guide

In today's interconnected threat landscape, the traditional perimeter-based security model is fundamentally broken. Modern attacks exploit identity compromise, phishing, and session hijacking, rendering network location irrelevant for trust decisions. Implementing Zero Trust security is no longer an option but a strategic imperative. This guide from SkyCore Solutions provides a comprehensive, authoritative framework for organizations looking to adopt a "never trust, always verify" posture, combining the architectural rigor of NIST SP 800-207, the maturity guidance of CISA, and the practical implementation power of Microsoft Azure's capabilities, particularly Microsoft Entra Conditional Access. By the end of this guide, you will have a clear, actionable roadmap to begin or advance your Zero Trust journey, fortifying your defenses against evolving cyber threats.

Prerequisites

  • An active Microsoft Azure subscription with sufficient credits.
  • Microsoft Entra ID P1 or P2 license (essential for Conditional Access and Identity Protection).
  • Administrative access to your Microsoft Entra tenant (Global Administrator, Security Administrator, or Conditional Access Administrator roles).
  • Basic understanding of networking, identity management, and cloud security concepts.
  • Inventory of critical applications, data, and user roles within your organization.

Step 1: Understand Core Principles and Develop a Strategic Roadmap

Before diving into technical configurations, it's crucial to grasp the foundational principles of Zero Trust and develop a phased strategic roadmap. NIST SP 800-207 and Microsoft's Zero Trust overview emphasize three core tenets: Verify Explicitly, Use Least Privilege Access, and Assume Breach. This paradigm shift means every access request, regardless of origin, must be authenticated and authorized using all available signals (user identity, device health, location, data classification, application sensitivity). Least privilege ensures users and workloads get only the necessary access for the shortest duration. Assuming breach means designing controls to limit impact and enable rapid detection and response, as attackers might already be operating inside. CISA's Zero Trust Maturity Model provides a valuable framework for structuring this adoption journey across Identity, Device, Network, Application Workload, Data, and Analytics & Automation pillars, recommending a gradual progression rather than a "big bang" approach.

# While no direct CLI command for strategic planning, documenting your strategy is key.
# Create a Zero Trust policy document outline (conceptual example)
echo '# Zero Trust Policy Document
## 1. Introduction and Guiding Principles
   - Never Trust, Always Verify
   - Verify Explicitly
   - Use Least Privilege Access
   - Assume Breach
## 2. Business Scenarios and Critical Risk Areas (Aligned with CISA Maturity Model)
   - Identify top 3-5 high-risk scenarios (e.g., admin access, sensitive data access).
## 3. Technology Pillars & Current State Assessment
   - Identity: MFA adoption, Identity Governance
   - Devices: MDM enrollment, compliance policies
   - Applications: SaaS, on-premises, custom apps
   - Data: Classification, encryption
   - Network: Segmentation strategy
   - Visibility & Automation: SIEM, SOAR
## 4. Phased Implementation Plan (Initial, Advanced, Optimal)
   - Define measurable outcomes for each phase.
## 5. Roles and Responsibilities
   - Security team, IT operations, business owners.
' > zerotrust-strategy.md

Portal alternative: Begin by organizing workshops with stakeholders (security, IT operations, business units) to define business scenarios, assess current security maturity, and identify critical assets and risk areas. Document this strategy in a central repository.

Confirmation: A clearly articulated Zero Trust strategy document, endorsed by leadership, defining principles, scope, and a phased implementation roadmap.

Common pitfall: Attempting to implement Zero Trust as a purely technical project without executive buy-in or a clear understanding of business objectives. This often leads to over-blocking, user frustration, and project failure. Involve business leaders early to define security outcomes for the organization, focusing on the most critical areas of risk.

Step 2: Establish a Strong Identity Foundation with Multifactor Authentication (MFA)

Identity is the primary control plane for Zero Trust (Microsoft, NIST). Every access request starts with an identity, whether user or workload. Implementing robust Multifactor Authentication (MFA) is the most impactful initial step. Microsoft Entra Conditional Access acts as the Zero Trust policy engine, enabling fine-grained control over when and how MFA is enforced, considering signals like user risk, device state, and location.

# Enable Microsoft Entra Security Defaults (if not already enabled for a quick start)
# Security Defaults enforce MFA for all users and block legacy authentication protocols.
az ad security-defaults enable --is-enabled true

# OR, for granular control, create a Conditional Access policy to require MFA for all users accessing all cloud apps.
# This example requires MFA for all users accessing any cloud application, excluding specific service principals or trusted locations if desired.

# 1. Define the Conditional Access policy JSON (adjust details as needed)
POLICY_NAME="Require MFA for All Cloud Apps"
POLICY_DISPLAY_NAME="SkyCore - All Users - Require MFA for All Cloud Apps"
POLICY_STATE="enabledForReporting" # Start with report-only mode to evaluate impact

POLICY_JSON='{
  "displayName": "'"$POLICY_DISPLAY_NAME"'",
  "state": "'"$POLICY_STATE"'",
  "conditions": {
    "users": {
      "includeUsers": ["All"],
      "excludeUsers": []
    },
    "applications": {
      "includeApplications": ["All"],
      "excludeApplications": []
    },
    "clientAppTypes": {
      "includeClientAppTypes": ["all"]
    }
  },
  "grantControls": {
    "operator": "OR",
    "builtInControls": ["Mfa"] # Require multifactor authentication
  }
}'

# 2. Create the Conditional Access policy
echo $POLICY_JSON | az ad conditional-access policy create --policy @-
  • az ad security-defaults enable --is-enabled true: Enables Microsoft Entra Security Defaults, a baseline set of security policies including MFA for all, blocking legacy authentication, and requiring admin MFA.
  • az ad conditional-access policy create --policy @-: Creates a new Conditional Access policy using a JSON input from stdin.
  • "includeUsers": ["All"]: Targets all users in the tenant.
  • "includeApplications": ["All"]: Targets all cloud applications.
  • "builtInControls": ["Mfa"]: Specifies that Multifactor Authentication is required for access.
  • "state": "enabledForReporting": Crucial for initial deployment, this deploys the policy in report-only mode, allowing you to monitor its impact without enforcing it. Change to "enabled" once thoroughly tested.

Portal alternative: Navigate to Microsoft Entra admin center > Protection > Conditional Access > Policies. Click "New policy". Under Assignments, select "Users and groups" (All users) and "Cloud apps or actions" (All cloud apps). Under Access controls > Grant, select "Require multifactor authentication". Set "Enable policy" to "Report-only" initially.

Confirmation: Users are prompted for MFA when accessing applications (in enabled mode). In report-only mode, review Conditional Access insights and reporting to ensure the policy applies as expected without blocking legitimate access.

Step 3: Secure Endpoints and Devices Through Compliance and Management

The device accessing resources is a critical signal in Zero Trust. As Cloudflare notes, protection follows the asset, not just the network. Conditional Access policies can enforce requirements for device health and compliance (Microsoft). This often involves integrating with a Mobile Device Management (MDM) solution like Microsoft Intune to mark devices as compliant and enroll them in Microsoft Entra ID (Azure AD Join or Hybrid Azure AD Join).

# Example: Create a Conditional Access policy requiring compliant devices
# This policy requires devices to be marked as compliant by Intune for access to specific applications.

# 1. Define the Conditional Access policy JSON
POLICY_NAME="Require Compliant Device for Sensitive Apps"
POLICY_DISPLAY_NAME="SkyCore - Access Sensitive Apps - Require Compliant Device"
POLICY_STATE="enabledForReporting"

POLICY_JSON='{
  "displayName": "'"$POLICY_DISPLAY_NAME"'",
  "state": "'"$POLICY_STATE"'",
  "conditions": {
    "users": {
      "includeUsers": ["All"]
    },
    "applications": {
      "includeApplications": ["00000002-0000-0000-c000-000000000000"] # Example: Microsoft Graph API. Replace with actual App IDs for sensitive apps.
    },
    "devicePlatforms": {
      "includeDevicePlatforms": ["all"]
    }
  },
  "grantControls": {
    "operator": "OR",
    "builtInControls": ["CompliantDevice"]
  }
}'

# 2. Create the Conditional Access policy
echo $POLICY_JSON | az ad conditional-access policy create --policy @-
  • "includeApplications": ["00000002-0000-0000-c000-000000000000"]: This GUID represents the Microsoft Graph API. For real-world use, replace this with the application IDs of your specific sensitive applications (e.g., your CRM, HR system, financial application).
  • "builtInControls": ["CompliantDevice"]: Requires the device accessing the application to be marked as compliant by an integrated MDM solution (like Intune).
  • Successful implementation of this policy requires a functional MDM solution to enroll and assess device compliance.

Portal alternative: In Microsoft Entra admin center > Protection > Conditional Access > Policies, create a new policy. Target users and groups, and specific cloud apps. Under Access controls > Grant, select "Require device to be marked as compliant". Set "Enable policy" to "Report-only".

Confirmation: Devices attempting to access targeted applications will be blocked or prompted to register/become compliant. Monitor Conditional Access sign-in logs for policy application details.

Common pitfall: Rolling out device compliance policies without adequate communication and enrollment procedures for end-users. This can lead to widespread access issues and productivity loss. Pilot with a small group, provide clear instructions for device enrollment and compliance, and have support channels ready.

Step 4: Implement Least Privilege Access with RBAC and Just-In-Time (JIT)

The principle of least privilege dictates that users and workloads should have only the minimum access necessary to perform their tasks, and only for the shortest time required. This is critical for limiting the potential impact of a compromised account, aligning with the "Assume Breach" principle (Microsoft, NIST). Azure Role-Based Access Control (RBAC) and Microsoft Entra Privileged Identity Management (PIM) are key tools here.

# Example: Assign a custom RBAC role with Just-In-Time access using PIM

# 1. Define a custom RBAC role (if built-in roles are too broad)
# This example creates a custom role that allows restarting Azure VMs.
# Save the JSON below as custom-vm-restart-role.json
# For this guide, let's assume a custom role definition is in place or a built-in role is used.

# 2. Get the role definition ID for a built-in role (e.g., Virtual Machine Contributor)
ROLE_NAME="Virtual Machine Contributor"
ROLE_DEFINITION_ID=$(az role definition list --name "$ROLE_NAME" --query "[0].id" -o tsv)

# 3. Get the object ID of the user or group to assign the role to
USER_UPN="user@yourdomain.com" # Replace with actual user UPN
USER_OBJECT_ID=$(az ad user show --id "$USER_UPN" --query "id" -o tsv)

# 4. Get the resource scope (e.g., a resource group ID)
RESOURCE_GROUP_NAME="my-sensitive-vms"
RESOURCE_GROUP_ID=$(az group show --name "$RESOURCE_GROUP_NAME" --query "id" -o tsv)

# 5. Assign the role to the user at the resource group scope (directly, for comparison)
# az role assignment create --assignee-object-id "$USER_OBJECT_ID" --role "$ROLE_DEFINITION_ID" --scope "$RESOURCE_GROUP_ID" --assignee-principal-type User

# 6. For Just-In-Time (JIT) access, use Microsoft Entra PIM for Azure resources.
# This is done via PowerShell for PIM assignments to Azure resources.
# Install Azure AD and Azure RM modules if not already present:
# Install-Module -Name AzureAD
# Install-Module -Name Az.Resources, Az.Pim

# PowerShell commands for PIM (conceptual for JIT enablement):
# Connect-AzureAD
# Connect-AzAccount
# 
# # Enable PIM for Azure resources for the specified role and user/group
# New-AzContext -Subscription "YourSubscriptionName" # Select correct subscription context
# 
# # Get PIM role definition for Azure resources (e.g., Virtual Machine Contributor)
# $roleDefinition = Get-AzPimRoleDefinition -Scope "/subscriptions/YourSubscriptionID" | Where-Object {$_.DisplayName -eq "Virtual Machine Contributor"}
# 
# # Get the principal (user/group) to make eligible
# $principal = Get-AzADUser -UserPrincipalName "user@yourdomain.com"
# 
# # Create an eligible assignment (PIM setup)
# New-AzPimRoleAssignment -Scope "/subscriptions/YourSubscriptionID/resourceGroups/$RESOURCE_GROUP_NAME" `
#     -RoleDefinitionId $roleDefinition.Id `
#     -ObjectId $principal.Id `
#     -AssignmentType "Eligible" `
#     -MaxDuration "PT8H" # Max 8 hours for activation
  • az role definition list: Retrieves existing RBAC role definitions.
  • az ad user show: Retrieves details about a Microsoft Entra user.
  • az group show: Retrieves details about an Azure resource group.
  • az role assignment create: Creates a direct, standing RBAC role assignment. For Zero Trust, this should be minimized in favor of JIT.
  • New-AzPimRoleAssignment (PowerShell): Creates an eligible role assignment in Azure PIM, meaning the user must activate the role for a limited time.
  • -AssignmentType "Eligible": Specifies that the assignment is for PIM eligibility, not a permanent role.
  • -MaxDuration "PT8H": Sets the maximum duration for which the role can be activated (e.g., 8 hours).

Portal alternative: For RBAC, navigate to a resource group, resource, or subscription > Access control (IAM) > Add > Add role assignment. For PIM, navigate to Microsoft Entra admin center > Identity Governance > Privileged Identity Management. Manage Azure resources, roles, and assignments, making users eligible rather than permanently assigned.

Confirmation: Verify that users only have standing access to roles absolutely essential for their baseline functions. For privileged roles, confirm that assignments are "Eligible" in PIM, requiring activation and justification for elevated access.

Step 5: Harden Applications and Workloads with Granular Access Policies

Applications, whether SaaS, on-premises, or custom-developed, represent significant attack surfaces. Zero Trust dictates that access to applications and the data they process must be explicitly verified and controlled. This extends to API security and ensuring only trusted application identities can interact. Conditional Access can also enforce policies directly on applications (Microsoft).

# Example: Create a Conditional Access policy requiring an approved client app and app protection policy
# This policy ensures that users access a specific SaaS application (e.g., Salesforce) only via an approved mobile app (e.g., Outlook Mobile) 
# that enforces Intune App Protection Policies (APP).

# 1. Define the Conditional Access policy JSON
POLICY_NAME="Require Approved App for SaaS App"
POLICY_DISPLAY_NAME="SkyCore - SaaS Access - Require Approved Client App"
POLICY_STATE="enabledForReporting"

POLICY_JSON='{
  "displayName": "'"$POLICY_DISPLAY_NAME"'",
  "state": "'"$POLICY_STATE"'",
  "conditions": {
    "users": {
      "includeUsers": ["All"]
    },
    "applications": {
      "includeApplications": ["your_saas_app_id"] # Replace with the Application ID of your SaaS app (e.g., Salesforce, Workday)
    },
    "clientAppTypes": {
      "includeClientAppTypes": ["mobileAppsAndDesktopClients"]
    }
  },
  "grantControls": {
    "operator": "OR",
    "builtInControls": ["ApprovedClientApp", "AppProtectionPolicy"]
  }
}'

# 2. Create the Conditional Access policy
echo $POLICY_JSON | az ad conditional-access policy create --policy @-
  • "includeApplications": ["your_saas_app_id"]: Replace your_saas_app_id with the actual Application ID of the target SaaS application. You can find this in the Microsoft Entra admin center under Enterprise Applications.
  • "builtInControls": ["ApprovedClientApp", "AppProtectionPolicy"]: Requires users to access the application via an approved client application (e.g., Microsoft Outlook Mobile, Microsoft Teams) *and* that an Intune App Protection Policy (APP) is applied to that client app. This helps protect organizational data even on unmanaged devices.

Portal alternative: In Microsoft Entra admin center > Protection > Conditional Access > Policies, create a new policy. Target users and groups, and specific cloud apps. Under Access controls > Grant, select "Require approved client app" and "Require app protection policy". Set "Enable policy" to "Report-only".

Confirmation: Users attempting to access the specified SaaS application from an unapproved client app or without an applied APP will be blocked. Monitor Conditional Access sign-in logs.

Step 6: Protect Data with Classification, Encryption, and Access Policies

Data is the ultimate asset, and protecting it is paramount in Zero Trust. NIST SP 800-207 highlights the need to protect data regardless of where it resides. This involves data classification, robust encryption (at rest and in transit), and implementing granular access policies based on sensitivity. Azure Information Protection (AIP) and Microsoft Purview (formerly Azure Purview) are crucial for discovering, classifying, and protecting sensitive data.

# Example: Configure a Storage Account to enforce secure access with TLS and restrict public access

# 1. Create a storage account (if not already existing)
STORAGE_ACCOUNT_NAME="skcdata01"
RESOURCE_GROUP_NAME="skc-data-rg"
LOCATION="eastus"

az group create --name "$RESOURCE_GROUP_NAME" --location "$LOCATION"
az storage account create --name "$STORAGE_ACCOUNT_NAME" --resource-group "$RESOURCE_GROUP_NAME" \
    --location "$LOCATION" --sku Standard_GRS --encryption-services blob file

# 2. Enforce HTTPS only (data in transit protection)
az storage account update --name "$STORAGE_ACCOUNT_NAME" --resource-group "$RESOURCE_GROUP_NAME" --https-only true

# 3. Restrict public network access (data at rest protection by restricting external access)
az storage account update --name "$STORAGE_ACCOUNT_NAME" --resource-group "$RESOURCE_GROUP_NAME" --public-network-access Disabled

# 4. Integrate with private endpoints for secure access (conceptual, typically done via VNet integration)
# az network private-endpoint create ... (requires VNet and subnet)

# 5. For data classification and labelling, utilize Azure Information Protection (AIP) or Microsoft Purview
# AIP PowerShell command to apply a sensitivity label (example: sensitivity.ps1)
# This is a conceptual example, actual implementation involves configuring AIP policies and client deployments.
# Connect-AipService
# Set-AipServiceOnboardingControlPolicy -OnboardingControlLevel All
# New-Label -Name "SkyCore Confidential" -Tooltip "Sensitive company information" -Enabled $true -EncryptionEnabled $true

# Or, using the Microsoft Purview client for scanning and labeling:
# Install and configure Purview Information Protection scanner on file shares or data sources.
# No direct CLI for applying Purview labels on files without client/scanner.
  • az storage account create ... --encryption-services blob file: Creates a storage account and enables encryption for blob and file services (at rest).
  • az storage account update ... --https-only true: Enforces that all communication with the storage account must use HTTPS, protecting data in transit.
  • az storage account update ... --public-network-access Disabled: Disables public internet access to the storage account, requiring access through private endpoints or specific Virtual Network (VNet) rules.
  • Azure Information Protection (AIP) PowerShell: Commands like New-Label are used to create sensitivity labels that can enforce encryption and access restrictions on documents and emails.

Portal alternative: For storage accounts, navigate to the storage account > Configuration, then toggle "Require secure transfer" to enabled and "Public network access" to disabled. For AIP/Purview, manage sensitivity labels and policies in the Microsoft Purview compliance portal. Manually apply labels in Office apps or deploy clients/scanners.

Confirmation: Sensitive data assets are identified and classified. Storage accounts enforce HTTPS and restricted network access. Labels are applied to documents, enforcing encryption and access controls.

Step 7: Micro-segment Networks and Enforce Network Access Control

While Zero Trust shifts focus from network perimeter, internal network segmentation (micro-segmentation) remains crucial for limiting lateral movement, aligning with the "Assume Breach" principle. NIST SP 800-207 describes a Zero Trust Architecture (ZTA) where enterprise assets are deployed in micro-segments, protected by Policy Enforcement Points (PEPs). Azure Network Security Groups (NSGs) and Azure Firewall are fundamental tools for this.

# Example: Create Network Security Groups (NSGs) for micro-segmentation

# 1. Create a Network Security Group for a web tier
NSG_WEB_NAME="skc-web-nsg"
RESOURCE_GROUP_NAME="skc-app-rg"
LOCATION="eastus"

az group create --name "$RESOURCE_GROUP_NAME" --location "$LOCATION"
az network nsg create --name "$NSG_WEB_NAME" --resource-group "$RESOURCE_GROUP_NAME" --location "$LOCATION"

# 2. Add an inbound rule to allow HTTP/HTTPS from the internet (for web servers)
az network nsg rule create --resource-group "$RESOURCE_GROUP_NAME" --nsg-name "$NSG_WEB_NAME" --name "Allow-HTTP-HTTPS-Inbound" \
    --priority 100 --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 80 443 --source-address-prefixes Internet

# 3. Add an inbound rule to allow database traffic from an app tier (example: SQL on port 1433)
NSG_APP_NAME="skc-app-nsg"
APP_SUBNET_CIDR="10.0.1.0/24" # CIDR of the application subnet

az network nsg rule create --resource-group "$RESOURCE_GROUP_NAME" --nsg-name "$NSG_WEB_NAME" --name "Allow-SQL-from-AppTier" \
    --priority 110 --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 1433 --source-address-prefixes "$APP_SUBNET_CIDR"

# 4. Associate the NSG to a subnet (example: web subnet)
VNET_NAME="skc-vnet"
WEB_SUBNET_NAME="web-subnet"

# Assume VNet and subnets already exist for this example
# az network vnet create ...
# az network vnet subnet create ...

az network vnet subnet update --resource-group "$RESOURCE_GROUP_NAME" --vnet-name "$VNET_NAME" --name "$WEB_SUBNET_NAME" \
    --network-security-group "$NSG_WEB_NAME"
  • az network nsg create: Creates a new Network Security Group.
  • az network nsg rule create: Adds an inbound or outbound security rule to an NSG.
  • --priority: Rules are processed in priority order (lower number first).
  • --direction Inbound / Outbound: Specifies the direction of traffic the rule applies to.
  • --source-address-prefixes Internet: Represents any IP address outside the VNet. For internal micro-segmentation, this would be specific CIDR blocks of other subnets.
  • az network vnet subnet update ... --network-security-group: Associates an NSG to a specific subnet, applying all its rules to traffic flowing in and out of that subnet.

Portal alternative: Navigate to Virtual networks > [Your VNet] > Subnets. Select a subnet, then associate an existing NSG or create a new one. Within the NSG blade, manage inbound and outbound security rules.

Confirmation: Verify network traffic flows only between authorized segments and ports using NSG flow logs and network watcher tools. Unauthorized traffic attempts should be explicitly denied by NSG rules.

Step 8: Leverage Visibility, Analytics, and Automation for Continuous Monitoring

Zero Trust is a dynamic, continuous process. The "never trust, always verify" principle requires constant monitoring, analysis of signals, and automated responses (Microsoft, NIST, CISA). Microsoft Entra ID Protection, Microsoft Defender suite, Azure Monitor, and Azure Sentinel provide the telemetry and capabilities for this. Real-time and calculated risk detection feeds into Conditional Access decisions, enabling adaptive policies.

# Example: Configure Microsoft Entra ID Protection policies (no direct CLI for policy creation, but for enabling features)
# Microsoft Entra ID Protection policies are primarily configured via the portal or Microsoft Graph API.
# Example for listing risky users (as an indicator of ID Protection functionality)

az rest --method GET --url "https://graph.microsoft.com/v1.0/identityProtection/riskyUsers" --query "value[].{Id:id, DisplayName:displayName, RiskLevel:riskLevel, RiskState:riskState}" -o table

# Example: Enable Microsoft Defender for Cloud (formerly Azure Security Center) for continuous assessment
# This enables cloud workload protection for various Azure resources.

# Enable standard tier for a subscription
SUBSCRIPTION_ID=$(az account show --query "id" -o tsv)
az security pricing create --name "VirtualMachines" --resource-group "$RESOURCE_GROUP_NAME" --subscription "$SUBSCRIPTION_ID" --tier Standard
az security pricing create --name "StorageAccounts" --resource-group "$RESOURCE_GROUP_NAME" --subscription "$SUBSCRIPTION_ID" --tier Standard

# Example: Deploy Azure Monitor Log Analytics Workspace and enable diagnostic settings for critical resources
# This provides a centralized logging platform for analysis.

WORKSPACE_NAME="skc-loganalytics"

az monitor log-analytics workspace create --resource-group "$RESOURCE_GROUP_NAME" --location "$LOCATION" --workspace-name "$WORKSPACE_NAME"

# Enable diagnostic settings for a Microsoft Entra ID (conceptual example, requires tenant ID)
# Note: This is typically configured via the Microsoft Entra admin center -> Diagnostic settings
# az monitor diagnostic-settings create --name "EntraIDAuditLogs" --resource "/providers/Microsoft.Aadiam/tenant/" --resource-group "$RESOURCE_GROUP_NAME" --logs '[{"category":"AuditLogs","enabled":true}]' --workspace "$WORKSPACE_NAME"

# General approach for diagnostic settings on resources (e.g., Key Vault)
KEYVAULT_NAME="skc-secrets"
az keyvault create --name "$KEYVAULT_NAME" --resource-group "$RESOURCE_GROUP_NAME" --location "$LOCATION"
az monitor diagnostic-settings create --name "KeyVaultAudit" --resource "/subscriptions/$SUBSCRIPTION_ID/resourceGroups/$RESOURCE_GROUP_NAME/providers/Microsoft.KeyVault/vaults/$KEYVAULT_NAME" \
    --logs '[{"categoryGroup":"audit","enabled":true}]' --metrics '[{"category":"AllMetrics","enabled":true}]' --workspace "$WORKSPACE_NAME"
  • az rest --method GET --url "https://graph.microsoft.com/v1.0/identityProtection/riskyUsers": Queries the Microsoft Graph API to list risky users detected by Microsoft Entra ID Protection. This is for observation, not configuration.
  • az security pricing create: Enables the Standard tier of Microsoft Defender for Cloud for specific resource types, providing advanced threat protection and vulnerability management.
  • az monitor log-analytics workspace create: Creates a centralized Log Analytics workspace for collecting logs and metrics.
  • az monitor diagnostic-settings create: Configures diagnostic settings for Azure resources to send their logs and metrics to the Log Analytics workspace for analysis.

Portal alternative: For Microsoft Entra ID Protection, navigate to Microsoft Entra admin center > Protection > Identity Protection to configure user and sign-in risk policies. For Defender for Cloud, navigate to Defender for Cloud > Environment settings. For Log Analytics and diagnostic settings, go to Azure Monitor > Log Analytics workspaces, then for individual resources, navigate to their respective blades > Monitoring > Diagnostic settings.

Confirmation: Risky sign-ins and users are detected by Identity Protection and can trigger Conditional Access policies. Logs from critical resources are flowing into Log Analytics. Defender for Cloud actively assesses resources and provides security recommendations.

Step 9: Cultivate a Culture of Security and Continuous Improvement

Zero Trust is a journey, not a destination. As CISA's maturity model emphasizes, it's a gradual, long-term effort requiring continuous evaluation and refinement. Security is everyone's job, not solely the responsibility of the security team (Microsoft). Foster a culture of security awareness, provide regular training, and encourage feedback to optimize policies. Regularly review your Zero Trust architecture and policies against evolving threats and business needs.

# While no direct CLI command for culture change, regular policy review is critical.
# Set up a recurring calendar reminder for policy review.
# (Conceptual command for a local system, indicating a recurring task)

echo "Review Zero Trust policies quarterly. Focus on Conditional Access, RBAC, and PIM assignments." > ~/Documents/ZeroTrustReviewReminder.txt

# Use Azure Automation or Azure DevOps for policy as code and continuous validation (conceptual):
# Azure CLI for managing Automation accounts and runbooks:
# az automation account create ...
# az automation runbook create ...

# Example for listing Conditional Access policies to facilitate review (part of audit)
az ad conditional-access policy list --query "[].{DisplayName:displayName, State:state, Id:id}" -o table
  • az ad conditional-access policy list: Lists all Conditional Access policies, useful for auditing and review.

Portal alternative: Schedule recurring reviews of Conditional Access policies, RBAC assignments, and PIM configurations within the respective Azure portal blades. Leverage the "What If" tool in Conditional Access to simulate changes before deployment. Conduct regular security awareness training for all employees.

Confirmation: A defined schedule for policy review and updates is in place. Security awareness programs are active. Policies are regularly adjusted based on monitoring data and organizational changes.
