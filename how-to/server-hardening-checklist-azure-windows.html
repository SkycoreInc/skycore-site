The Definitive Server Hardening Checklist for Azure and Windows Environments

In an era of relentless cyber threats, a comprehensive "server hardening checklist" is not merely a recommendation—it's a foundational requirement for any secure IT infrastructure. As a senior IT consultant at SkyCore Solutions, we understand that robust server security is paramount for protecting your data, maintaining operational continuity, and achieving compliance. This guide provides a detailed, authoritative, and CLI-first approach to hardening your Windows Server and Azure-based virtual machines, synthesizing best practices from Microsoft and CIS Benchmarks. By the end of this guide, you will have a clear, actionable plan to significantly enhance the security posture of your servers, reducing attack surfaces and fortifying defenses against sophisticated adversaries.

Prerequisites

  • Administrative access to your Windows Server instance(s) (local or domain).
  • Azure subscription with appropriate permissions (Contributor or Security Admin roles).
  • Basic understanding of PowerShell, Azure CLI, and Group Policy management.
  • A change management process in place for applying security configurations in production environments.
  • Backup of critical systems before implementing changes, especially in production.
  • Access to CIS Benchmarks for Windows Server (free PDF available for non-commercial use, or via CIS SecureSuite membership for automated tools and detailed guidance).

Step 1: Inventory and Baseline Security

Before making any changes, it's crucial to understand your current environment. Removing unnecessary software, roles, and features significantly reduces the attack surface, aligning with the principle of "least functionality" recommended by both Microsoft and CIS Benchmarks.

# Get a list of installed Windows Features
Get-WindowsFeature | Where-Object {$_.InstallState -eq 'Installed'} | Select-Object Name, InstallState

# To remove a specific Windows Feature (example: Telnet-Client)
Remove-WindowsFeature -Name Telnet-Client -Restart

# To get a list of installed applications
Get-WmiObject -Class Win32_Product | Select-Object Name, Version, Vendor
  • -Name: Specifies the name of the Windows Feature to remove.
  • -Restart: Restarts the computer if required by the feature removal.

Portal alternative: In Server Manager, navigate to "Manage" > "Remove Roles and Features." Follow the wizard to deselect and remove any roles or features not essential for the server's function. For applications, use "Apps & features" in Windows Settings.

Confirmation: Rerun Get-WindowsFeature and verify the removed feature's InstallState is no longer 'Installed'. For applications, verify they no longer appear in the list.

Step 2: Implement Robust Patch Management

Regular patching is arguably the most fundamental security control. Windows Server Security documentation implicitly highlights this by focusing on protections "built into the operating system." CIS Benchmarks consistently emphasize keeping systems updated to mitigate known vulnerabilities effectively.

# Configure Windows Update for automatic downloads and scheduled installations
Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update" -Name "AUOptions" -Value 4
Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update" -Name "ScheduledInstallDay" -Value 0 # Every day
Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update" -Name "ScheduledInstallTime" -Value 3 # 3 AM

# Trigger an immediate check for updates
wuauclt.exe /detectnow
  • AUOptions: Specifies how Automatic Updates handles updates. 4 means "Auto download and schedule the install."
  • ScheduledInstallDay: Sets the day of the week for scheduled installations (0-7, 0 is every day, 1 is Sunday, etc.).
  • ScheduledInstallTime: Sets the time of day for scheduled installations (0-23, representing hours).
  • /detectnow: Forces the Windows Update client to immediately check for new updates.

Portal alternative: Navigate to "Settings" > "Update & Security" > "Windows Update." Configure "Advanced options" for update deferral and active hours.

Confirmation: Check the Windows Update history or review event logs to confirm updates are being downloaded and installed.

Step 3: Fortify Account and Authentication Security (PAM, JEA, Credential Guard)

Privileged access is a primary target for attackers. Microsoft's documentation emphasizes Privileged Access Management (PAM), Just Enough Administration (JEA), Just In Time (JIT) Administration, and Credential Guard to protect credentials. CIS Benchmarks also heavily recommend strong password policies and account lockout.

# Configure strong password policy via Group Policy (example for minimum password length)
# This is typically done via Group Policy Objects (GPOs) linked to OUs, not local commands.
# For local policy, use secpol.msc or the following:
# (Note: Best managed domain-wide via GPO for consistency)

# To configure minimum password length (example: 14 characters)
# Open Local Security Policy (secpol.msc) -> Account Policies -> Password Policy
# Set "Minimum password length" to 14 characters.

# To enable Credential Guard (requires UEFI with Secure Boot and TPM 2.0)
# (Note: This is an advanced feature and requires specific hardware/VM configurations)
# This typically involves deploying a Guarded Fabric and configuring Shielded VMs.
# A simplified approach for enabling via Group Policy on supported systems:
# Computer Configuration > Administrative Templates > System > Device Guard > Turn On Virtualization Based Security
# Set "Enable Virtualization Based Security" to Enabled.
# Set "Select Platform Security Level" to "Secure Boot and DMA Protection".
# Set "Credential Guard Configuration" to "Enabled with UEFI Lock".

# Example for Just Enough Administration (JEA) configuration (requires a session configuration file .pssc)
# (This is a complex setup. Consult Microsoft documentation for full JEA deployment.)
# 1. Create a PSSC file (e.g., JEAConfig.pssc)
# New-PSSessionConfigurationFile -Path 'C:\JEAConfig.pssc' -SessionType RestrictedRemoteServer -TranscriptDirectory 'C:\JEA_Transcripts' -RunAsVirtualAccount -RoleDefinitions @{ 'RoleName' = @{ VisibleCmdlets = 'Get-Service', 'Restart-Service' } }

# 2. Register the JEA endpoint
# Register-PSSessionConfiguration -Path 'C:\JEAConfig.pssc' -Name 'JEAEndpoint' -Force

# 3. Grant users access to the endpoint (example)
# Grant-PSSessionConfiguration -Name 'JEAEndpoint' -RoleName 'RoleName' -Principal 'DOMAIN\UserGroup'

# To enable Remote Credential Guard (for RDP sessions)
# This is a Group Policy setting: Computer Configuration > Administrative Templates > System > Credentials Delegation
# "Restrict delegation of credentials to remote servers" - Set to Enabled.
# "Allow delegation of default credentials with NTLM-only server authentication" - Set to Enabled.
# "Require Remote Credential Guard" - Set to Enabled.
  • New-PSSessionConfigurationFile: Creates a new PowerShell session configuration file.
  • -Path: Specifies the output path for the .pssc file.
  • -SessionType RestrictedRemoteServer: Configures the session to use a virtual account and restricts operations.
  • -TranscriptDirectory: Specifies a directory for storing transcripts of JEA sessions.
  • -RunAsVirtualAccount: Specifies that commands in the JEA session run as a temporary virtual account.
  • -RoleDefinitions: Defines roles with allowed cmdlets and parameters.
  • Register-PSSessionConfiguration: Registers the session configuration with PowerShell Remoting.
  • -Name: Specifies the name of the session configuration.
  • -Force: Overwrites an existing session configuration if one exists with the same name.
  • Grant-PSSessionConfiguration: Grants users or groups access to a JEA endpoint.
  • -Principal: Specifies the user or group to grant access.

Portal alternative: Credential Guard and Guarded Fabric require specific Azure VM SKUs and deployment patterns. JEA is configured via PowerShell. For general password policies, use Azure Active Directory (AAD) password protection or local GPOs.

Common pitfall: Implementing Credential Guard, Shielded VMs, and a full JEA/PAM solution is complex and requires careful planning and testing. Incorrect configurations can lead to inaccessible systems or reduced functionality. Always test in a non-production environment first. For Shielded VMs, ensure your Hyper-V hosts are configured as a "Guarded Fabric."

Confirmation: Verify JEA endpoint registration with Get-PSSessionConfiguration. For Credential Guard, check System Information (msinfo32.exe) under "Virtualization-based security" and "Credential Guard."

Step 4: Configure Network Security and Segmentation

Network security is fundamental. Azure best practices emphasize strong network controls, logical segmentation using subnets, and Network Security Groups (NSGs). Windows Server's Datacenter Firewall also provides host-based protection. Zero Trust principles dictate that implicit trust based on network location is eliminated.

# Configure Windows Defender Firewall (host-based firewall) - example: block all incoming except RDP
# (Note: This assumes RDP is managed separately, e.g., via NSG for Azure VMs)
# First, block all inbound traffic by default profile settings (often done via GPO)
# Set-NetFirewallProfile -Name Public,Private,Domain -DefaultInboundAction Block

# To allow specific inbound ports (e.g., RDP on port 3389)
New-NetFirewallRule -DisplayName "Allow RDP Inbound" -Direction Inbound -LocalPort 3389 -Protocol TCP -Action Allow -Enabled True -Profile Any

# For Azure Network Security Groups (NSGs) - Azure CLI example
# (Requires resource group, VNet, Subnet names)
# To create an NSG
az network nsg create --resource-group SkyCoreRG --name SkyCoreNSG

# To create an inbound rule for RDP (port 3389)
az network nsg rule create --resource-group SkyCoreRG --nsg-name SkyCoreNSG --name AllowRDP --priority 100 --direction Inbound --source-address-prefixes VirtualNetwork --source-port-ranges '*' --destination-address-prefixes '*' --destination-port-ranges 3389 --protocol Tcp --access Allow

# To associate NSG with a subnet
az network vnet subnet update --resource-group SkyCoreRG --vnet-name SkyCoreVNet --name SkyCoreSubnet --network-security-group SkyCoreNSG

# To create Application Security Groups (ASGs) for simpler rule management
az network asg create --resource-group SkyCoreRG --name WebServersASG --location eastus
az network asg create --resource-group SkyCoreRG --name DatabaseServersASG --location eastus

# To add a VM network interface to an ASG
az network nic ip-config update --resource-group SkyCoreRG --nic-name SkyCoreVMNic --vnet-name SkyCoreVNet --subnet-name SkyCoreSubnet --name ipconfig1 --application-security-groups WebServersASG
  • Set-NetFirewallProfile: Modifies properties of a network firewall profile.
  • -DefaultInboundAction Block: Sets the default action for incoming traffic to block.
  • New-NetFirewallRule: Creates a new Windows Defender Firewall rule.
  • -DisplayName: User-friendly name for the rule.
  • -Direction Inbound: Specifies the direction of traffic the rule applies to.
  • -LocalPort: Specifies the local port number.
  • -Protocol TCP: Specifies the protocol (TCP, UDP, Any).
  • -Action Allow: Specifies whether to allow or block traffic.
  • -Enabled True: Enables the rule.
  • -Profile Any: Applies the rule to all network profiles (Domain, Private, Public).
  • az network nsg create: Creates an Azure Network Security Group.
  • --resource-group: Specifies the resource group.
  • --name: Name of the NSG.
  • az network nsg rule create: Creates an inbound/outbound security rule.
  • --priority: Rule processing order (lower numbers processed first).
  • --direction: Inbound or Outbound.
  • --source-address-prefixes: Source IP ranges (e.g., VirtualNetwork, Internet, specific CIDR).
  • --destination-port-ranges: Port range for the destination.
  • az network vnet subnet update: Updates a virtual network subnet.
  • --network-security-group: Associates the NSG with the subnet.
  • az network asg create: Creates an Application Security Group.
  • az network nic ip-config update: Updates an IP configuration on a network interface.
  • --application-security-groups: Associates the NIC with the ASG.

Portal alternative: For Windows Firewall: "Control Panel" > "Windows Defender Firewall" > "Advanced settings." For Azure NSGs and ASGs: Navigate to "Network security groups" or "Application security groups" in the Azure portal and configure rules.

Confirmation: Use Get-NetFirewallRule to verify host firewall rules. In Azure, review the NSG rules and ASG associations in the portal. Test network access from various sources.

Step 5: Secure DNS Services

DNS is a critical service often overlooked in hardening efforts. Windows Server provides "What's New in DNS in Windows Server," which implies continuous improvements in its security posture. Securing your DNS infrastructure prevents common attacks like DNS spoofing and cache poisoning, a recommendation echoed by CIS Benchmarks.

# Enable DNSSEC validation (requires DNSSEC-aware resolvers and signed zones)
# This is a complex setup involving DNS zone signing.
# Example command for enabling validation on a DNS resolver:
# (Note: This assumes your DNS server is configured as a resolver and upstream servers support DNSSEC.)
# Open DNS Manager -> Right-click server -> Properties -> Advanced tab -> Enable DNSSEC validation

# To restrict dynamic updates to secure-only
# This is a per-zone setting:
# Set-DnsServerZone -Name "skycore.local" -Type Primary -DynamicUpdate Secure
  • Set-DnsServerZone: Modifies properties of a DNS zone.
  • -Name: Specifies the name of the DNS zone.
  • -DynamicUpdate Secure: Allows only secure dynamic updates using authenticated credentials.

Portal alternative: For Azure DNS, services are managed by Microsoft. For DNS on Azure VMs, manage directly on the Windows Server via DNS Manager console.

Confirmation: Use dnscmd /Info /GlobalQueryBlockList to check DNS settings and ensure dynamic updates are secure. Test DNS resolution for signed zones.

Step 6: Implement Application Control (WDAC)

Windows Defender Application Control (WDAC) is a powerful security feature that restricts which applications can run on your servers. Microsoft's documentation provides a dedicated "WDAC Deployment Guide," highlighting its importance in blocking malicious execution. This is a critical defense against malware and unauthorized software, a core tenet of system integrity.

# (Note: WDAC deployment is a multi-step process. This provides an overview of policy creation.)
# 1. Generate a base WDAC policy XML (example: allow Microsoft, Windows, and WHQL apps)
New-CIPolicy -FilePath "C:\Temp\BasePolicy.xml" -Level Publisher -Fallback Hash -ScanPath C:\Windows,C:\ProgramFiles

# 2. Add rules for specific applications or signers if needed
# Example: Add a rule for an application not covered by the base policy
# Add-SignerRule -FilePath "C:\Temp\BasePolicy.xml" -CertificatePath "C:\Path\To\AppSigner.cer" -UserModeEnabled

# 3. Convert the policy XML to binary format
ConvertFrom-CIPolicy -FilePath "C:\Temp\BasePolicy.xml" -BinaryFilePath "C:\Windows\System32\CodeIntegrity\CiPolicies\Active\BasePolicy.bin"

# 4. Deploy the policy (typically via Group Policy or MDM)
# Group Policy: Computer Configuration > Administrative Templates > System > Device Guard > Deploy Windows Defender Application Control
# Set to Enabled and specify the path to your .bin file.
  • New-CIPolicy: Creates a new Windows Defender Application Control policy.
  • -FilePath: Specifies the output path for the policy XML file.
  • -Level Publisher: Specifies the file rule level (e.g., Publisher, Hash, FileName). Publisher allows executables signed by trusted publishers.
  • -Fallback Hash: Specifies a fallback rule level if the primary level fails.
  • -ScanPath: Specifies paths to scan for initial applications to include in the policy.
  • ConvertFrom-CIPolicy: Converts a WDAC policy XML file to its binary format for deployment.
  • -BinaryFilePath: Specifies the output path for the binary policy file.

Portal alternative: WDAC policies are configured and deployed via Group Policy or MDM, not directly through the Azure portal. For Azure VMs, manage policies within the guest OS.

Common pitfall: Incorrectly configured WDAC policies can prevent essential applications or even the operating system itself from functioning. Thorough testing is paramount, especially in 'audit mode' before enforcing. Start with a strict policy and gradually open it, rather than the reverse.

Confirmation: After deployment via GPO, verify policy enforcement using Event Viewer (Applications and Services Logs > Microsoft > Windows > CodeIntegrity > Operational).

Step 7: Configure Transport Layer Security (TLS) Settings

Secure communication protocols are vital. Microsoft's documentation includes "Transport Layer Security Registry Settings" as a hardening area. Disabling weak cipher suites and older TLS versions (like TLS 1.0/1.1) prevents man-in-the-middle attacks and ensures data confidentiality. CIS Benchmarks also strongly recommend this for all server roles.

# Disable TLS 1.0 and TLS 1.1 (Client and Server)
# (Note: Check application compatibility before disabling older TLS versions)

# Disable TLS 1.0 Client
New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' -Force | Out-Null
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' -Name 'Enabled' -Value 0 -Type DWord -Force
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' -Name 'DisabledByDefault' -Value 1 -Type DWord -Force

# Disable TLS 1.0 Server
New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' -Force | Out-Null
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' -Name 'Enabled' -Value 0 -Type DWord -Force
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' -Name 'DisabledByDefault' -Value 1 -Type DWord -Force

# Repeat similar steps for TLS 1.1. Ensure TLS 1.2 and 1.3 are enabled and prioritized.
# To ensure TLS 1.2 is enabled and prioritized (usually default on modern OS, but good to check)
# New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Client' -Force | Out-Null
# Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Client' -Name 'Enabled' -Value 1 -Type DWord -Force
# Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.2\Client' -Name 'DisabledByDefault' -Value 0 -Type DWord -Force
# (Repeat for Server)
  • New-Item: Creates a new registry key.
  • -Path: Specifies the full path to the registry key.
  • -Force: Creates parent keys if they don't exist and overwrites existing keys/values.
  • Set-ItemProperty: Sets the value of a property at the specified location.
  • -Name: Name of the property (e.g., 'Enabled', 'DisabledByDefault').
  • -Value: The value to set (0 for disabled, 1 for enabled).
  • -Type DWord: Specifies the data type of the registry value.

Portal alternative: Registry changes are made within the guest OS. No direct Azure portal configuration for this.

Confirmation: After a reboot, use a tool like Nmap's ssl-enum-ciphers script or an online SSL/TLS scanner against public-facing services to verify that older TLS versions are disabled. Internally, test applications that rely on TLS.

Step 8: Enable Comprehensive Auditing and Logging

Detecting and responding to threats requires detailed visibility. Microsoft highlights "Detecting and Responding to Threats" and mentions Microsoft Operations Management Suite (OMS). Azure's network best practices recommend "Virtual network flow logs for comprehensive traffic visibility." CIS Benchmarks consistently emphasize robust auditing to ensure accountability and forensic capability.

# Configure advanced audit policy settings (via Group Policy for domain-joined, or auditpol for local)
# Example: Enable 'Audit Process Creation' for forensic analysis
auditpol /set /subcategory:"Process Creation" /success:enable /failure:enable

# Example: Enable 'Audit Logon' events
auditpol /set /subcategory:"Logon" /success:enable /failure:enable

# To get current audit policy settings
auditpol /get /category:*

# For Azure Virtual Network Flow Logs (Azure CLI)
# (Requires Storage Account, Log Analytics Workspace for full functionality)
# To enable flow logs on a VNet
az network watcher flow-log create --resource-group SkyCoreRG --location eastus --name SkyCoreVNetFlowLog --nsg SkyCoreNSG --storage-account SkyCoreStorageAccount --interval 10 --format JSON --version 2 --traffic-analytics enabled --workspace SkyCoreLogAnalyticsWorkspaceID
  • auditpol /set: Configures audit policy settings.
  • /subcategory: Specifies the audit subcategory (e.g., "Process Creation").
  • /success:enable: Enables auditing of successful events.
  • /failure:enable: Enables auditing of failed events.
  • az network watcher flow-log create: Creates a flow log for a Network Security Group (NSG) or Virtual Network (VNet).
  • --nsg: The name or ID of the NSG to enable flow logging on. (Note: Azure now recommends VNet flow logs over NSG flow logs for broader coverage.)
  • --storage-account: The ID or name of the storage account to store flow logs.
  • --interval: The interval in minutes to capture flow logs (e.g., 10 minutes).
  • --format JSON: Specifies the output format.
  • --version 2: Specifies the version of the flow log schema.
  • --traffic-analytics enabled: Enables Traffic Analytics for deeper insights.
  • --workspace: The ID of the Log Analytics Workspace for Traffic Analytics.

Portal alternative: For Windows auditing: "Local Security Policy" (secpol.msc) > "Advanced Audit Policy Configuration." For Azure Flow Logs: "Network Watcher" > "Flow logs" in the Azure portal.

Confirmation: Check Event Viewer (Security log) for new audit events correlating to the enabled policies. In Azure, navigate to your storage account and verify flow log files are being generated, or check the Traffic Analytics dashboard in Log Analytics.

Step 9: Implement Secure Boot and Guarded Fabric (for VMs)

For virtualized environments, protecting the integrity of the VM from the underlying host is crucial. Microsoft provides "Secure virtualization with Shielded VMs" and a "Guarded Fabric Deployment Guide." Secured-core servers provide hardware-level protection, ensuring the boot chain is trusted from the firmware up.

# (Note: This is largely a Hyper-V Host and Azure infrastructure configuration, not guest OS)

# For Secured-core server (requires compatible hardware, typically pre-configured by OEM)
# No direct command to "enable" in guest OS; it's a platform capability.
# Verify VBS status in System Information (msinfo32.exe) under "Virtualization-based security"

# For Shielded VMs on Hyper-V:
# (Requires a Host Guardian Service (HGS) and shielded VM template)
# This is typically configured via Hyper-V Manager and HGS management consoles.
# Example from Hyper-V host to create a shielded VM:
# New-VM -Name "ShieldedVM01" -Shielded -Path "C:\VMs" -Generation 2 -MemoryStartupBytes 4GB -ProcessorCount 2 -VHDPath "C:\VMs\ShieldedVM01.vhdx" -TemplateDisk "C:\ShieldedVMs\TemplateDisk.vhdx" -Guardian "HGSCluster"

# For Azure confidential computing VMs (equivalent to Secured-core/Shielded VMs concept)
# When deploying an Azure VM: select a confidential VM size (e.g., DCasv5-series or ECasv5-series)
# Use Azure CLI to deploy a confidential VM (example):
az vm create --resource-group SkyCoreRG --name ConfidentialVM --image "WindowsServer2022Datacenter" --size Standard_DC2as_v5 --admin-username azureuser --admin-password "P@ssw0rd12345!" --location eastus --security-type TrustedLaunch --enable-vtpm --enable-secure-boot
  • az vm create: Creates a new Azure Virtual Machine.
  • --security-type TrustedLaunch: Enables Trusted Launch, which includes Secure Boot and vTPM.
  • --enable-vtpm: Enables the virtual Trusted Platform Module.
  • --enable-secure-boot: Enables Secure Boot for the VM.

Portal alternative: When creating a new VM in Azure, select "Trusted launch virtual machine" under the "Security type" option on the "Security" tab. For Hyper-V Shielded VMs, use Hyper-V Manager and the Host Guardian Service console.

Confirmation: For Azure VMs, verify Trusted Launch and Secure Boot are enabled in the VM's "Security" blade in the Azure portal. For on-premises Shielded VMs, check the VM configuration in Hyper-V Manager and confirm its health status on the HGS server.

Step 10: Regularly Review and Automate Compliance

Hardening is not a one-time event. Security posture drifts over time, and new threats emerge. Continuous monitoring and enforcement against benchmarks like CIS are crucial. Microsoft Cloud Security Benchmark provides prescriptive security controls with Azure Policy enforcement for ongoing compliance.

# For Azure Policy to enforce security configurations
# (Example: Audit VMs not using Trusted Launch)
# az policy assignment create --name "Audit-VMs-NoTrustedLaunch" --display-name "Audit VMs without Trusted Launch" --scope "/subscriptions/YOUR_SUBSCRIPTION_ID" --policy "YOUR_POLICY_DEFINITION_ID" --enforcement-mode Default

# Example policy definition (conceptual, actual definitions are JSON files)
# Policy to audit VMs that do not have Secure Boot enabled
# Search for built-in policy: "Virtual machines should use Trusted Launch"

# Use CIS-CAT Pro Assessor for automated scanning against CIS Benchmarks
# (Requires CIS SecureSuite Membership)
# CIS-CAT Pro Assessor command line example (conceptual, consult CIS-CAT documentation):
# C:\CIS-CAT\cis-cat-pro-assessor.bat -b "CIS_Microsoft_Windows_Server_2022_Benchmark_v5.0.0.xml" -r "report.html" -o "C:\Reports"

# Manually generate a security report
Get-ComputerInfo -Property OsName, OsVersion, OsHardwareAbstractionLayer, HypervisorPresent, SecureBootEnabled, TPMPresent | Format-List
  • az policy assignment create: Creates an Azure Policy assignment.
  • --scope: The scope at which the policy assignment applies (e.g., subscription, resource group).
  • --policy: The ID or name of the policy definition.
  • --enforcement-mode Default: Enforces the policy; DoNotEnforce is for audit-only.

Portal alternative: Azure Policy assignments are managed under "Policy" in the Azure portal. CIS Benchmarks can be manually reviewed (PDF) or automatically assessed with CIS-CAT Pro (requires external tool).

Confirmation: Regularly review Azure Policy compliance dashboards and CIS-CAT Pro Assessor reports. Schedule regular security audits and penetration tests.

Common pitfall: The "break-fix" mentality of security hardening can lead to significant downtime. Never implement changes in a production environment without thorough testing in a staging environment that mirrors production. Automated deployment and rollback strategies are essential.
Common pitfall: Over-hardening can lead to reduced usability or break legitimate business applications. A balanced approach is crucial, focusing on risk reduction while maintaining operational efficiency. Document all changes and their justifications.
