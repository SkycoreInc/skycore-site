Your Essential Azure Monitor Log Analytics Setup Guide for SMBs

At SkyCore Solutions, we understand that for SMBs, maintaining robust, secure, and performant IT infrastructure is paramount, often with limited resources. The challenge of gaining comprehensive visibility into your cloud environment can feel daunting. This is where Azure Monitor, Microsoft's unified observability service, becomes an indispensable tool. Specifically, this Azure Monitor Log Analytics setup guide will walk you through establishing a central hub for all your operational logs.

By the end of this guide, you will have a fully functional Azure Log Analytics workspace, configured to collect critical telemetry from your Azure resources. This will empower your team to proactively monitor performance, enhance security posture, streamline troubleshooting, and comply with audit requirements – all without requiring enterprise-grade complexity or budget.

Prerequisites

  • Azure Subscription: An active Azure subscription. A free account is sufficient for initial testing.
  • Permissions: An Azure account with permissions to create and manage resources within a resource group. Specifically, you will need Microsoft.OperationalInsights/workspaces/write permissions, typically granted by roles like "Log Analytics Contributor" or "Owner" for the target resource group.
  • Azure CLI / Azure PowerShell: Either Azure CLI (version 2.x or later) or the Azure PowerShell Az module (version 5.x or later) installed and configured on your local machine or via Azure Cloud Shell.
  • Estimated Cost: Log Analytics primarily uses a consumption-based pricing model. The recommended "PerGB2018" tier charges per GB of data ingested and optionally for data retention beyond 31 days. For SMBs, initial costs are typically low (e.g., $2.76 CAD per GB ingested in Canada Central at time of writing) and scale with your usage.

Step 1: Introduction to Azure Monitor Log Analytics for SMBs

Before we dive into the technical steps, it's crucial to understand why Log Analytics is a game-changer for SMBs. Azure Monitor collects various types of telemetry – logs, metrics, traces, and events – from your entire cloud and hybrid environment. Log Analytics is the powerful tool within Azure Monitor specifically designed to collect, store, query, and analyze your log data. For an SMB, this means:

  • Centralized Visibility: Instead of disparate logs across VMs, network devices, and Azure services, all your critical operational data resides in one searchable location.
  • Proactive Troubleshooting: Quickly diagnose issues by correlating logs across different systems.
  • Enhanced Security: Monitor for suspicious activities, audit user actions, and gain insights into potential threats.
  • Cost Optimization: Identify underutilized resources or anomalous usage patterns.
  • Compliance Readiness: Maintain historical records of operations for audit and compliance purposes.

This centralized data platform also underpins other critical Azure services like Microsoft Defender for Cloud and Microsoft Sentinel, ensuring your investment in Log Analytics has broader benefits.

Step 2: Prerequisites and Planning Your Log Analytics Workspace

A Log Analytics workspace is your dedicated data store within Azure Monitor. Proper planning ensures efficient operation and cost management. As SkyCore Solutions operates from Montreal, we'll use canadacentral as our example region, which is often ideal for Canadian SMBs due to data residency and latency considerations.

First, ensure you are logged into your Azure subscription:

az login
Connect-AzAccount

Next, we recommend creating a dedicated resource group for your monitoring resources. This simplifies management and access control.

az group create --name rg-skycore-monitoring --location canadacentral
  • --name rg-skycore-monitoring: A logical name for your resource group. We recommend a naming convention that indicates its purpose.
  • --location canadacentral: The Azure region where your resource group will reside. Choose a region geographically close to your primary operations or other Azure resources for optimal performance and data residency.

Portal alternative: Navigate to "Resource groups" in the Azure portal, click "Create", provide a name (e.g., rg-skycore-monitoring) and select a region (e.g., "Canada Central").

Pro tip: While you can use an existing resource group, creating a dedicated one for monitoring (e.g., rg-skycore-monitoring) allows for easier application of granular Role-Based Access Control (RBAC) and lifecycle management. This segregation is a best practice for SMBs to maintain a clean and manageable Azure environment.

Step 3: Creating the Azure Log Analytics Workspace

Now, let's create the Log Analytics workspace itself. This will be the central repository for all your collected logs. For SMBs, the "PerGB2018" pricing tier is generally the most flexible and cost-effective as it charges based on actual data ingestion, scaling with your needs.

az monitor log-analytics workspace create \
    --resource-group rg-skycore-monitoring \
    --workspace-name la-skycore-prod \
    --location canadacentral \
    --sku PerGB2018
  • --resource-group rg-skycore-monitoring: The resource group we created in the previous step.
  • --workspace-name la-skycore-prod: A unique name for your Log Analytics workspace within your subscription. Ensure it's descriptive, for example, la-<company>-<environment>.
  • --location canadacentral: The region for your workspace. This should ideally match your resource group and the majority of the resources you intend to monitor.
  • --sku PerGB2018: This is the recommended pricing tier for most SMBs. It offers a pay-as-you-go model for data ingestion. Other SKUs exist, but "PerGB2018" provides good flexibility without upfront commitments.
New-AzOperationalInsightsWorkspace `
    -ResourceGroupName "rg-skycore-monitoring" `
    -Name "la-skycore-prod" `
    -Location "canadacentral" `
    -Sku "PerGB2018"

Portal alternative: 1. In the Azure portal search bar, type "Log Analytics workspaces" and select it. 2. Click "Create". 3. On the "Basics" tab: - Subscription: Select your Azure subscription. - Resource group: Choose rg-skycore-monitoring. - Name: Enter la-skycore-prod. - Region: Select "Canada Central". 4. Click "Review + create" and then "Create".

Run this to verify:

az monitor log-analytics workspace show --resource-group rg-skycore-monitoring --workspace-name la-skycore-prod --query "{name:name, location:location, sku:sku.name}" -o table
Get-AzOperationalInsightsWorkspace -ResourceGroupName "rg-skycore-monitoring" -Name "la-skycore-prod" | Format-Table Name, Location, Sku

This command will display the name, location, and SKU of your newly created workspace, confirming its successful deployment.

Step 4: Configuring Data Collection: Azure Activity Log

With your workspace ready, the next crucial step in this Azure Monitor Log Analytics setup guide is to start collecting data. The Azure Activity Log provides insights into subscription-level events, such as when a resource is created, deleted, or updated. This is fundamental for security, auditing, and understanding administrative changes in your environment.

We'll configure diagnostic settings to send the Activity Log to our Log Analytics workspace.

az monitor diagnostic-settings create \
    --name "SendActivityLogToLA" \
    --resource "/subscriptions/<your-subscription-id>" \
    --logs "[{category: 'Administrative', enabled: true}, {category: 'Security', enabled: true}, {category: 'ServiceHealth', enabled: true}]" \
    --workspace la-skycore-prod \
    --resource-group rg-skycore-monitoring \
    --event-hub-name '' \
    --storage-account-id ''
  • --name "SendActivityLogToLA": A descriptive name for your diagnostic setting.
  • --resource "/subscriptions/<your-subscription-id>": This targets your entire subscription. Replace <your-subscription-id> with your actual Azure subscription ID. You can get it by running az account show --query id -o tsv.
  • --logs "[{category: 'Administrative', enabled: true}, {category: 'Security', enabled: true}, {category: 'ServiceHealth', enabled: true}]": Specifies which categories of Activity Log to send. For SMBs, "Administrative", "Security", and "ServiceHealth" are essential to capture.
  • --workspace la-skycore-prod: The name of your Log Analytics workspace.
  • --resource-group rg-skycore-monitoring: The resource group where your workspace resides.
  • --event-hub-name '' and --storage-account-id '': We leave these blank as we are sending logs directly to Log Analytics.
$workspaceId = (Get-AzOperationalInsightsWorkspace -ResourceGroupName "rg-skycore-monitoring" -Name "la-skycore-prod").ResourceId
$subscriptionId = (Get-AzContext).Subscription.Id
New-AzDiagnosticSetting `
    -Name "SendActivityLogToLA" `
    -ResourceId "/subscriptions/$subscriptionId" `
    -LogActionGroup "Administrative" `
    -LogActionGroup "Security" `
    -LogActionGroup "ServiceHealth" `
    -WorkspaceId $workspaceId `
    -Enabled $true

Portal alternative: 1. In the Azure portal, search for "Monitor" and select it. 2. In the left-hand menu, under "Settings", click "Diagnostic settings". 3. Click "Add diagnostic setting". 4. Under "Scope", ensure your subscription is selected. 5. Provide a "Diagnostic setting name" (e.g., SendActivityLogToLA). 6. Under "Categories", select "Administrative", "Security", and "ServiceHealth". 7. Under "Destination details", check "Send to Log Analytics workspace". 8. Select your Subscription and la-skycore-prod as the "Log Analytics workspace". 9. Click "Save".

Run this to verify: Wait a few minutes for data to start flowing, then query your workspace.

az monitor log-analytics query --workspace la-skycore-prod --analytics-query "AzureActivity | take 5" --timespan 5m
$query = "AzureActivity | take 5"
Invoke-AzOperationalInsightsQuery -WorkspaceName "la-skycore-prod" -Query $query -Timespan (New-TimeSpan -Minutes 5)

If you see results, your Activity Log is successfully sending data to Log Analytics.

Step 5: Configuring Data Collection: Azure Virtual Machines (via AMA)

Monitoring your Azure Virtual Machines is critical for understanding performance, identifying issues, and maintaining security. Microsoft now recommends using the Azure Monitor Agent (AMA) over the legacy Log Analytics agent for comprehensive guest-level collection. This step outlines how to deploy AMA to an existing Azure VM.

Common pitfall: Azure Monitor Agent (AMA) vs. Log Analytics Agent: Ensure you are using the Azure Monitor Agent (AMA) for new deployments. While the legacy Log Analytics agent still functions, AMA offers superior performance, security, and simpler management through Data Collection Rules (DCRs). Migrating from the legacy agent to AMA is recommended for all SMBs.

First, you need to create a Data Collection Rule (DCR) which defines what data to collect and where to send it. For simplicity, we'll create a basic DCR to collect Windows event logs (System, Security, Application) and performance counters.

Create a DCR JSON file (e.g., basic-dcr.json):

{
  "properties": {
    "dataSources": {
      "windowsEventLogs": [
        {
          "streams": ["Microsoft-WindowsEvent"],
          "dataSourceId": "windowsEventLogs-1",
          "xPathQueries": [
            "Event!*[System[(Level=1 or Level=2 or Level=3 or Level=4 or Level=0)]]",
            "Security!*[System[(Level=1 or Level=2 or Level=3 or Level=4 or Level=0)]]",
            "Application!*[System[(Level=1 or Level=2 or Level=3 or Level=4 or Level=0)]]"
          ]
        }
      ],
      "performanceCounters": [
        {
          "streams": ["Microsoft-InsightsMetrics"],
          "dataSourceId": "perfCounters-1",
          "samplingFrequencyInSeconds": 60,
          "counterSpecifiers": [
            "\\Processor(_Total)\\% Processor Time",
            "\\Memory\\Available MBytes",
            "\\LogicalDisk(_Total)\\% Free Space",
            "\\Network Interface(*)\\Bytes Total/sec"
          ]
        }
      ]
    },
    "destinations": {
      "logAnalytics": [
        {
          "workspaceResourceId": "/subscriptions/<your-subscription-id>/resourceGroups/rg-skycore-monitoring/providers/Microsoft.OperationalInsights/workspaces/la-skycore-prod",
          "name": "la-skycore-prod-destination"
        }
      ]
    },
    "dataFlows": [
      {
        "streams": [
          "Microsoft-WindowsEvent",
          "Microsoft-InsightsMetrics"
        ],
        "destinations": ["la-skycore-prod-destination"]
      }
    ]
  }
}

IMPORTANT: Replace <your-subscription-id> with your actual Azure subscription ID in the workspaceResourceId field.

Now, create the DCR using the CLI:

az monitor data-collection rule create \
    --resource-group rg-skycore-monitoring \
    --rule-name dcr-skycore-windows-vms \
    --location canadacentral \
    --json-file basic-dcr.json
  • --resource-group rg-skycore-monitoring: Your monitoring resource group.
  • --rule-name dcr-skycore-windows-vms: A name for your Data Collection Rule.
  • --location canadacentral: The region for the DCR.
  • --json-file basic-dcr.json: Path to the DCR definition file you created.

Next, associate the DCR with your target Azure VM. Replace <your-vm-name> and <your-vm-resource-group> with your VM's details.

az vm extension set \
    --name AzureMonitorWindowsAgent \
    --publisher Microsoft.Azure.Monitor \
    --resource-group <your-vm-resource-group> \
    --vm-name <your-vm-name> \
    --enable-auto-upgrade true \
    --settings "{\"dataCollectionRuleResourceId\":\"/subscriptions/<your-subscription-id>/resourceGroups/rg-skycore-monitoring/providers/Microsoft.Insights/dataCollectionRules/dcr-skycore-windows-vms\"}"
  • --name AzureMonitorWindowsAgent: The name of the Azure Monitor Agent extension for Windows. (For Linux, use AzureMonitorLinuxAgent).
  • --resource-group <your-vm-resource-group>: The resource group where your VM is located.
  • --vm-name <your-vm-name>: The name of the virtual machine you want to monitor.
  • --settings "{\"dataCollectionRuleResourceId\":\"...\"}": Specifies the DCR to apply. Remember to replace <your-subscription-id>. Note the escaped double quotes.
# First, get your DCR's Resource ID
$dcr = Get-AzDataCollectionRule -ResourceGroupName "rg-skycore-monitoring" -Name "dcr-skycore-windows-vms"

# Get your VM object
$vm = Get-AzVM -ResourceGroupName "<your-vm-resource-group>" -Name "<your-vm-name>"

# Set the Azure Monitor Agent extension
Set-AzVMExtension `
    -ResourceGroupName $vm.ResourceGroupName `
    -VMName $vm.Name `
    -Name "AzureMonitorWindowsAgent" `
    -Publisher "Microsoft.Azure.Monitor" `
    -ExtensionType "AzureMonitorWindowsAgent" `
    -TypeHandlerVersion "1.0" `
    -EnableAutomaticUpgrade `
    -Setting @{"dataCollectionRuleResourceId"=$dcr.Id}

Portal alternative: 1. In the Azure portal, navigate to your Log Analytics workspace (la-skycore-prod). 2. Under "Settings", select "Data Collection Rules" and click "Create" to define your DCR. - Configure "Resources" (select your VMs), "Collect and deliver" (specify event logs and performance counters, send to your LA workspace). 3. Alternatively, for a specific VM: - Navigate to your Virtual Machine in the Azure portal. - In the left-hand menu, under "Monitoring", select "Insights". - Click "Enable" and follow the prompts. This process guides you through creating a default DCR and associating it with the VM.

Run this to verify: Allow 5-10 minutes for the agent to install and data to flow.

az monitor log-analytics query --workspace la-skycore-prod --analytics-query "Event | where Computer == '<your-vm-name>' | take 5" --timespan 15m
$query = "Event | where Computer == '<your-vm-name>' | take 5"
Invoke-AzOperationalInsightsQuery -WorkspaceName "la-skycore-prod" -Query $query -Timespan (New-TimeSpan -Minutes 15)

Replace <your-vm-name> with your actual VM name. If events are returned, your VM is successfully sending log data.

Step 6: Configuring Data Collection: Other Azure Resources

Beyond Activity Logs and VMs, most Azure services (e.g., Azure SQL Database, App Services, Key Vault, Azure Firewall) can send their diagnostic logs and metrics to a Log Analytics workspace. This is done via diagnostic settings, similar to how we configured the Activity Log, but applied at the resource level.

The process is consistent for most Azure resources. Here's a generic example for an Azure Key Vault:

az monitor diagnostic-settings create \
    --name "SendKeyVaultLogsToLA" \
    --resource "/subscriptions/<your-subscription-id>/resourceGroups/<your-keyvault-resource-group>/providers/Microsoft.KeyVault/vaults/<your-keyvault-name>" \
    --logs "[{category: 'AuditEvent', enabled: true}]" \
    --metrics "[{category: 'AllMetrics', enabled: true}]" \
    --workspace la-skycore-prod \
    --resource-group rg-skycore-monitoring
  • --resource "...": The full Azure Resource ID of the service you want to monitor. You can find this in the resource's "Properties" blade in the Azure portal or via az resource show --name <resource-name> --resource-group <resource-group> --query id -o tsv.
  • --logs: A JSON array specifying which log categories to send. Available categories vary by service (e.g., "AuditEvent" for Key Vault, "AppServiceHTTPLogs" for App Services).
  • --metrics: A JSON array specifying which metrics to send. "AllMetrics" is common.
$workspaceId = (Get-AzOperationalInsightsWorkspace -ResourceGroupName "rg-skycore-monitoring" -Name "la-skycore-prod").ResourceId
$keyVaultResourceId = (Get-AzKeyVault -ResourceGroupName "<your-keyvault-resource-group>" -VaultName "<your-keyvault-name>").ResourceId
New-AzDiagnosticSetting `
    -Name "SendKeyVaultLogsToLA" `
    -ResourceId $keyVaultResourceId `
    -Log "AuditEvent" `
    -Metric "AllMetrics" `
    -WorkspaceId $workspaceId `
    -Enabled $true

Portal alternative: 1. Navigate to the specific Azure resource (e.g., your Azure SQL Database, App Service, Key Vault) in the Azure portal. 2. In the left-hand menu, under "Monitoring", select "Diagnostic settings". 3. Click "Add diagnostic setting". 4. Provide a name, check "Send to Log Analytics workspace", select your subscription and la-skycore-prod. 5. Select the relevant log categories and metrics you wish to collect for that specific service. 6. Click "Save".

Run this to verify: Wait a few minutes for data to flow.

az monitor log-analytics query --workspace la-skycore-prod --analytics-query "AzureDiagnostics | where ResourceProvider == 'MICROSOFT.KEYVAULT' | take 5" --timespan 15m
$query = "AzureDiagnostics | where ResourceProvider == 'MICROSOFT.KEYVAULT' | take 5"
Invoke-AzOperationalInsightsQuery -WorkspaceName "la-skycore-prod" -Query $query -Timespan (New-TimeSpan -Minutes 15)

Replace MICROSOFT.KEYVAULT with the appropriate resource provider (e.g., MICROSOFT.WEB for App Services) and check for results.

Step 7: Exploring Your Data with Log Analytics Queries (KQL)

The power of Log Analytics truly comes alive with Kusto Query Language (KQL). KQL is a robust and intuitive query language designed for exploring and analyzing large datasets. This is where you transform raw logs into actionable insights.

To access the Log Analytics query interface:

Portal steps: 1. In the Azure portal, search for "Log Analytics workspaces" and select la-skycore-prod. 2. In the left-hand menu, under "General", select "Logs".

You'll see a query editor. The left sidebar lists available tables (e.g., AzureActivity, Event, AzureDiagnostics). Here are a few basic KQL examples to get you started:

AzureActivity
| take 10
| project TimeGenerated, OperationName, ResourceGroup, Caller
  • This query retrieves the 10 most recent entries from the AzureActivity table and displays specific columns (project).
Event
| where TimeGenerated > ago(1h)
| where EventID == 4624 // Successful logon event for Windows
| project TimeGenerated, Computer, Account, Activity
  • This query filters the Event table for events within the last hour, specifically for successful Windows logons (Event ID 4624), projecting relevant details.
AzureDiagnostics
| where ResourceProvider == "MICROSOFT.WEB"
| summarize count() by OperationName
| order by count_ desc
  • This query counts operations from Azure App Services (MICROSOFT.WEB) and groups them by OperationName, showing which operations are most frequent.
Pro tip: Use Simple Mode first: If KQL seems daunting, start with the "Simple mode" in the Log Analytics query editor. It provides a spreadsheet-like experience with point-and-click filtering and sorting. As you build queries in Simple mode, you can switch to "KQL mode" to see the underlying KQL query, which is an excellent way to learn!
