The Definitive Windows Server Hardening Checklist for 2026

In an era where cyber threats are increasingly sophisticated, securing your core infrastructure is not just a best practice—it's a critical imperative. Windows Servers, often the backbone of an organization's operations, are prime targets for malicious actors. Without a rigorous approach to security, these systems become vulnerable entry points, leading to data breaches, operational downtime, and severe reputational damage. This comprehensive Windows Server hardening checklist provides SkyCore Solutions' authoritative, CLI-first methodology to lock down your server environment, ensuring resilience against a wide spectrum of attacks. By the end of this guide, you will have implemented robust security controls, transforming your Windows Servers into fortified digital assets.

Prerequisites

  • Administrative access to your Windows Server instance(s)
  • Familiarity with PowerShell and Group Policy Management
  • A robust backup and recovery strategy in place
  • Understanding of your application dependencies and network topology
  • Downtime window for server reboots or service restarts for critical changes

Step 1: Establish a Baseline and Remove Unnecessary Components

Before implementing advanced security measures, it's critical to start with a clean, minimal baseline by removing any roles or features not essential for the server's function and ensuring the system is fully patched. This reduces the attack surface significantly, as attackers cannot exploit services that do not exist.

First, identify and remove unnecessary Windows features and roles. This is a fundamental step in minimizing the attack surface. For example, if a server isn't acting as a DHCP server, that role should be removed.

Get-WindowsFeature | Where-Object {$_.Installed -eq $true -and $_.Name -notmatch "^(" + ((Get-WindowsFeature -Name Server-Core, Server-Gui-Shell, Telnet-Client | Select-Object -ExpandProperty Name) -join "|")) + ")$"} | Format-Table Name, Installed
  • Get-WindowsFeature: Retrieves information about Windows features.
  • Where-Object {$_.Installed -eq $true -and $_.Name -notmatch ...}: Filters for installed features that are NOT core components or expected GUI elements (adjust regex as needed). This command primarily serves to *identify* features.
  • Format-Table Name, Installed: Displays the names and installation status in a table.

To remove a specific feature, use:

Remove-WindowsFeature -Name "Feature-Name-Here" -Remove
  • Remove-WindowsFeature: Uninstalls specified roles or features.
  • -Name "Feature-Name-Here": Specifies the exact name of the feature to remove.
  • -Remove: Ensures that the feature files are also removed from the server, freeing up disk space and preventing reinstallation without source media.

Portal alternative: Open Server Manager, navigate to 'Manage' > 'Remove Roles and Features'. Follow the wizard to deselect and remove unnecessary components.

Verify that only essential roles and features remain installed by re-running Get-WindowsFeature | Where-Object {$_.Installed -eq $true} and reviewing the output.

Next, ensure automatic updates are configured and functioning correctly. While often managed by WSUS or SCCM in enterprise environments, direct configuration is crucial for standalone servers or those not under central update management. Microsoft emphasizes timely patching to address emerging threats.

Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update" -Name "AUOptions" -Value 4
Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update" -Name "ScheduledInstallDay" -Value 0 # Every Day
Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update" -Name "ScheduledInstallTime" -Value 3 # 3 AM
  • Set-ItemProperty: Modifies a property of an item in the registry.
  • -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update": Specifies the registry path for Windows Update settings.
  • -Name "AUOptions" -Value 4: Configures automatic updates to 'Download updates automatically and install them on the specified schedule'.
  • -Name "ScheduledInstallDay" -Value 0: Sets the installation schedule to 'Every Day'.
  • -Name "ScheduledInstallTime" -Value 3: Sets the installation time to 3 AM.

Portal alternative: Navigate to Settings > Update & Security > Windows Update > Advanced options. Configure 'Automatic (recommended)' and set active hours if not centrally managed.

You can verify current settings with `Get-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\WindowsUpdate\Auto Update"`.

Common pitfall: Over-hardening by indiscriminately removing features can lead to application breakage or unexpected service outages. Always perform thorough testing in a staging environment before applying changes to production servers, and ensure you understand the dependencies of your critical applications.

Step 2: Configure Robust Antivirus and Endpoint Detection & Response (EDR)

Leverage Windows Defender Antivirus and integrate it with an EDR solution to provide active, real-time protection against malware and advanced threats, ensuring timely updates and careful exclusion management. Microsoft explicitly states that Windows Defender Antivirus is built into Windows Server 2016 and later, offering immediate and active protection.

First, ensure Windows Defender Antivirus is enabled and running. Unlike client versions, Windows Defender Antivirus on Server 2016 and above will not disable itself if another antivirus product is present, providing an additional layer of defense.

Get-MpComputerStatus | Select-Object AntivirusEnabled, RealTimeProtectionEnabled, FullScanEndTime, SignatureLastUpdated
  • Get-MpComputerStatus: Retrieves the current status of Windows Defender Antivirus.
  • Select-Object AntivirusEnabled, RealTimeProtectionEnabled, FullScanEndTime, SignatureLastUpdated: Displays key status indicators to confirm operational readiness.

If not enabled (rare on modern Server OS):

Set-MpPreference -DisableRealtimeMonitoring $false
  • Set-MpPreference: Configures settings for Windows Defender Antivirus.
  • -DisableRealtimeMonitoring $false: Ensures real-time protection is enabled.

Next, ensure antivirus definitions are up-to-date. This is critical as new threats emerge daily.

Update-MpSignature
  • Update-MpSignature: Initiates an immediate update of antivirus and anti-spyware definitions.

Portal alternative: Open Windows Security (or Defender Security Center) > Virus & threat protection > Virus & threat protection updates > Check for updates.

While exclusions should be used sparingly and only when absolutely necessary, they can prevent performance issues or application conflicts. Exercise extreme caution, as exclusions create potential security blind spots.

Add-MpPreference -ExclusionPath "C:\Path\To\Exclude"
Add-MpPreference -ExclusionProcess "process.exe"
  • Add-MpPreference: Adds preferences for Windows Defender Antivirus.
  • -ExclusionPath "C:\Path\To\Exclude": Specifies a file path to exclude from scans.
  • -ExclusionProcess "process.exe": Specifies a process to exclude from real-time monitoring.

Verify exclusions with `Get-MpPreference | Select-Object ExclusionPath, ExclusionProcess`.

Step 3: Harden Network Security via Firewall and TLS Configuration

Implement stringent network access controls by configuring Windows Firewall to follow the principle of least privilege and enhance transport layer security by disabling weak protocols and ciphers. The Microsoft documentation emphasizes the importance of the Datacenter Firewall for network security.

Start by configuring Windows Firewall profiles to block inbound connections by default and only allow specific necessary traffic. This is a crucial defense against unauthorized network access.

Set-NetFirewallProfile -Name Domain,Private,Public -Enabled True -DefaultInboundAction Block -DefaultOutboundAction Allow
  • Set-NetFirewallProfile: Modifies settings for specified firewall profiles.
  • -Name Domain,Private,Public: Applies changes to all three network profiles.
  • -Enabled True: Ensures the firewall is active for these profiles.
  • -DefaultInboundAction Block: Blocks all inbound connections unless explicitly allowed by a rule.
  • -DefaultOutboundAction Allow: Allows all outbound connections by default (often modified in high-security environments).

Next, create specific inbound rules for services that *must* be accessible (e.g., RDP, HTTP/S). Always restrict source IP addresses where possible.

New-NetFirewallRule -DisplayName "Allow RDP from Admin Network" -Direction Inbound -LocalPort 3389 -Protocol TCP -Action Allow -RemoteAddress "192.168.1.0/24"
New-NetFirewallRule -DisplayName "Allow HTTPS to Web Server" -Direction Inbound -LocalPort 443 -Protocol TCP -Action Allow
  • New-NetFirewallRule: Creates a new firewall rule.
  • -DisplayName: A human-readable name for the rule.
  • -Direction Inbound: Specifies that the rule applies to incoming traffic.
  • -LocalPort: The destination port on the local server.
  • -Protocol TCP: Specifies the TCP protocol.
  • -Action Allow: Permits traffic matching the rule.
  • -RemoteAddress "192.168.1.0/24": Restricts access to a specific IP range (highly recommended for management services).

Portal alternative: Open 'Windows Defender Firewall with Advanced Security' > 'Inbound Rules' > 'New Rule'. Follow the wizard to configure ports, protocols, and scopes.

Common pitfall: Incorrectly configured firewall rules can lead to legitimate services being inaccessible, effectively taking your server offline. Always test new firewall rules in a controlled environment and have a rollback plan. When hardening TLS, incorrect registry edits can break connectivity to other systems or services that rely on older protocols.

To harden Transport Layer Security (TLS) settings, disable older, insecure protocols like TLS 1.0 and 1.1, and potentially weak cipher suites. Microsoft's documentation highlights the importance of TLS registry settings. This is often done via Group Policy, but direct registry modification is also possible.

# Disable TLS 1.0 for client-side connections
New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' -Force | Out-Null
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' -Name 'Enabled' -Value 0 -Force
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client' -Name 'DisabledByDefault' -Value 1 -Force

# Disable TLS 1.0 for server-side connections
New-Item 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' -Force | Out-Null
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' -Name 'Enabled' -Value 0 -Force
Set-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Server' -Name 'DisabledByDefault' -Value 1 -Force

# Repeat for TLS 1.1 if not required by legacy applications
# ...
  • New-Item: Creates a new registry key.
  • Set-ItemProperty: Modifies registry key properties.
  • -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.0\Client': Specifies the registry path for client-side TLS 1.0 settings.
  • -Name 'Enabled' -Value 0: Disables the protocol.
  • -Name 'DisabledByDefault' -Value 1: Ensures it's disabled by default.

A server reboot is often required for these TLS changes to take full effect. Verify TLS settings using an online scanner or by attempting to connect from clients configured to use only specific TLS versions.

Step 4: Implement Privileged Access Management (PAM) and Credential Protection

Minimize the risk of credential theft and abuse by adopting Just Enough Administration (JEA) for granular access control and enabling Credential Guard to protect derived domain credentials. Microsoft provides extensive documentation on Privileged Access Management (PAM), Just Enough Administration (JEA), and Credential Protection, including Credential Guard and Remote Credential Guard.

Just Enough Administration (JEA) allows you to delegate administrative tasks with minimal privileges. Instead of granting full administrator rights, you define specific tasks users can perform via a PowerShell endpoint. Setting up JEA is an extensive process that involves creating a session configuration file (`.pssc`), a role capability file (`.psrc`), and registering the configuration. Here, we provide a conceptual overview and the command to register a session configuration once files are prepared.

# Example: Registering a JEA endpoint (requires .pssc and .psrc files to be prepared)
Register-PSSessionConfiguration -Name "LimitedAdmin" -Path "C:\JEA\LimitedAdmin.pssc" -Force
  • Register-PSSessionConfiguration: Registers a new PowerShell session configuration on the local computer.
  • -Name "LimitedAdmin": The name of the JEA endpoint.
  • -Path "C:\JEA\LimitedAdmin.pssc": The path to the session configuration file you've created.
  • -Force: Overwrites an existing session configuration if one with the same name exists.

Portal alternative: JEA is primarily PowerShell-driven. While no direct GUI exists, tools like Azure AD Privileged Identity Management (PIM) offer similar JIT capabilities for Azure-connected resources.

After registration, users can connect to the JEA endpoint using `Enter-PSSession -ConfigurationName LimitedAdmin` and only execute permitted commands.

Credential Guard helps protect derived domain credentials by using virtualization-based security (VBS) to isolate secrets. This makes it significantly harder for attackers to perform pass-the-hash attacks. Enabling Credential Guard typically requires a secured-core server, UEFI, Secure Boot, and TPM 2.0. It's often configured via Group Policy or specific tooling.

# This example command is for enabling VBS and Credential Guard on a Hyper-V host and requires specific hardware and OS versions.
# For configuration via Group Policy, navigate to Computer Configuration > Administrative Templates > System > Device Guard > Turn On Virtualization Based Security.
Enable-VBS -VMHost -CredGuard -Force
  • Enable-VBS: Cmdlet from the DeviceGuardTools module (often installed manually or via specific features) to configure Virtualization-Based Security.
  • -VMHost: Specifies that the command applies to the Hyper-V host.
  • -CredGuard: Enables Credential Guard.
  • -Force: Proceeds without prompting for confirmation.

Portal alternative: Group Policy Management Editor (gpmc.msc) is the primary GUI for configuring Credential Guard on domain-joined servers. Navigate to Computer Configuration > Administrative Templates > System > Device Guard > 'Turn On Virtualization Based Security'. Set to 'Enabled' and configure 'Credential Guard' option.

Verify Credential Guard status using `System Information` (`msinfo32.exe`) and check 'Virtualization-based security running'. Also, review event logs for Device Guard events.

Step 5: Enforce Application Control and Advanced OS Hardening

Restrict unauthorized application execution using Windows Defender Application Control (WDAC) and apply comprehensive operating system hardening configurations based on industry benchmarks like CIS. Microsoft emphasizes WDAC and secured-core server as key components for OS and application hardening, while CIS Benchmarks provide detailed, consensus-driven guidelines.

Windows Defender Application Control (WDAC) allows you to control which drivers and applications are allowed to run on your Windows Server. This is one of the most effective ways to block malware and unauthorized software. Implementing WDAC is a multi-step process involving policy creation, auditing, and enforcement. Here's a conceptual command for generating a base policy:

# Example: Create a base WDAC policy from a reference computer
New-CIPolicy -FilePath "C:\WDAC\MyBasePolicy.xml" -Level Publisher -Fallback Hash -ScanPath "C:\"
ConvertFrom-CIPolicy -FilePath "C:\WDAC\MyBasePolicy.xml" -BinaryFilePath "C:\WDAC\MyBasePolicy.bin"
Copy-Item "C:\WDAC\MyBasePolicy.bin" "C:\Windows\System32\CodeIntegrity\CiPolicies\Active\{GUID}.cip"
  • New-CIPolicy: Generates a new Code Integrity policy from a reference system.
  • -FilePath: Specifies the output path for the XML policy.
  • -Level Publisher: Uses the publisher information to sign files, providing a strong trust level.
  • -Fallback Hash: Falls back to file hash if publisher info isn't available.
  • -ScanPath: The directory to scan for applications to include in the policy.
  • ConvertFrom-CIPolicy: Converts the XML policy into a binary format for deployment.
  • Copy-Item: Deploys the binary policy. The `{GUID}.cip` format is crucial.

Portal alternative: WDAC is primarily PowerShell-driven. For deployment, Group Policy can be used to distribute policies (Computer Configuration > Administrative Templates > System > Device Guard > Deploy Code Integrity Policy).

After deployment, monitor the 'CodeIntegrity' event log for any blocked applications or policy errors. WDAC should always be rolled out in audit mode first to prevent application breakage.

For comprehensive OS hardening, leverage the CIS Microsoft Windows Server Benchmarks. These benchmarks provide a community-consensus driven set of secure configuration guidelines. While the full benchmark is a detailed PDF, it can be implemented manually, via Group Policy Objects (GPOs), or using tools like CIS-CAT Pro Assessor and Build Kits.

A common CIS recommendation is to disable SMBv1, a legacy protocol with known vulnerabilities. This is an excellent example of reducing attack surface.

# Disable SMBv1 client
Disable-WindowsOptionalFeature -Online -FeatureName "SMB1Protocol" -Remove

# Disable SMBv1 server via registry
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters" -Name "SMB1" -Value 0 -Force
  • Disable-WindowsOptionalFeature: Disables an optional Windows feature.
  • -Online: Applies the change to the running operating system.
  • -FeatureName "SMB1Protocol": Specifies the SMBv1 client feature.
  • -Remove: Also removes the feature's files.
  • Set-ItemProperty: Modifies a registry value to disable the SMBv1 server component.

Portal alternative: Open 'Turn Windows features on or off' (optionalfeatures.exe) and uncheck 'SMB 1.0/CIFS File Sharing Support'. For registry, use regedit.exe.

Verify by checking `Get-WindowsOptionalFeature -Online -FeatureName "SMB1Protocol"` (should show Disabled) and `Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters" -Name "SMB1"` (should show 0).

Common pitfall: Implementing WDAC in enforce mode without thorough testing in audit mode can lead to applications failing to launch, potentially causing severe operational disruption. Always start with audit mode, collect logs, adjust the policy, and gradually move to enforce mode. Also, blindly applying CIS Benchmarks without understanding your environment can lead to service disruptions or application incompatibilities.

Step 6: Configure Comprehensive Auditing and Centralized Logging

Establish detailed auditing policies to monitor critical security events and ensure these logs are centrally collected and analyzed to detect and respond to threats effectively. Microsoft documentation highlights detecting and responding to threats, often involving Microsoft Operations Management Suite (OMS) and Advanced Threat Analytics (ATA).

Configure advanced audit policies to capture crucial security events. This provides visibility into user activities, system changes, and potential security incidents. Many of these are specified in CIS benchmarks.

# Example: Configure audit policy for account logon events
auditpol /set /category:"Account Logon" /subcategory:"Credential Validation" /success:enable /failure:enable

# Example: Configure audit policy for process creation
auditpol /set /category:"Detailed Tracking" /subcategory:"Process Creation" /success:enable /failure:enable
  • auditpol /set: Configures audit policies.
  • /category:"Account Logon": Specifies the audit category.
  • /subcategory:"Credential Validation": Specifies the audit subcategory.
  • /success:enable /failure:enable: Enables auditing for both successful and failed attempts.

Portal alternative: Group Policy Management Editor (gpmc.msc) > Computer Configuration > Policies > Windows Settings > Security Settings > Advanced Audit Policy Configuration > Audit Policies.

To view current audit policies, use `auditpol /get /category:*`.

Ensure event logs are configured for appropriate retention and size to avoid critical security events being overwritten too quickly. This helps ensure sufficient data is available for forensic analysis.

# Configure Security Log to overwrite events as needed, max size 1GB
wevtutil sl Security /ms:1073741824 /o:true
  • wevtutil sl Security: Targets the Security event log.
  • /ms:1073741824: Sets the maximum log size to 1 GB (1024 MB * 1024 KB * 1024 bytes).
  • /o:true: Configures the log to overwrite events as needed (oldest events are overwritten first).

Portal alternative: Open Event Viewer (eventvwr.msc) > Windows Logs > Security > Properties. Adjust 'Maximum log size' and 'When maximum event log size is reached'.

Verify settings by checking the Security log properties in Event Viewer or using `wevtutil get-log Security`.

Finally, centralize your server logs to a Security Information and Event Management (SIEM) system or a centralized log management solution. This is crucial for aggregated analysis, correlation of events across multiple systems, and timely alerting on suspicious activities. Microsoft Operations Management Suite (OMS), now largely integrated into Azure Monitor and Azure Sentinel, provides robust capabilities for this.

# Example: Install Log Analytics Agent (formerly OMS Agent) for Azure Monitor
# This assumes you have your Workspace ID and Primary Key.
# Download the agent from Azure portal, then run:
# "C:\Path\To\MMASetup-AMD64.exe" /qn ADD_OPINSIGHTS_WORKSPACE="YOUR_WORKSPACE_ID" ADD_OPINSIGHTS_WORKSPACE_KEY="YOUR_PRIMARY_KEY" AcceptEndUserLicenseAgreement=true
  • The command shown is a silent installation of the Log Analytics agent, which connects your server to an Azure Monitor Log Analytics Workspace for centralized logging.
  • ADD_OPINSIGHTS_WORKSPACE: Your unique Workspace ID from Azure.
  • ADD_OPINSIGHTS_WORKSPACE_KEY: The primary key for your Workspace.

Portal alternative: In the Azure portal, navigate to your Log Analytics workspace, go to 'Agents' > 'Windows servers', download the agent, and manually install it following the wizard, providing the Workspace ID and Key.

After installation, verify connectivity by checking the 'Operations Manager' event log for agent activity and looking for your server's data flowing into the Azure Log Analytics Workspace.
