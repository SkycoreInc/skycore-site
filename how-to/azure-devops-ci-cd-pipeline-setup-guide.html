Mastering Your Workflow: The Azure DevOps CI CD Pipeline Setup Guide for SMBs

For Small to Medium-sized Businesses (SMBs) in Montreal and beyond, efficient software delivery is paramount. Manual build, test, and deployment processes are not only time-consuming but also prone to human error, stifling innovation and delaying market entry. This is where a robust Continuous Integration (CI) and Continuous Delivery (CD) pipeline becomes a game-changer. This comprehensive Azure DevOps CI CD pipeline setup guide from SkyCore Solutions will walk you through establishing an automated, reliable, and scalable pipeline. By the end of this guide, you’ll have a working CI pipeline that automatically builds, tests, and prepares your application for deployment with every code change, setting the stage for true continuous delivery.

Prerequisites

  • An active Azure subscription for billing (required for free parallel jobs, see note below on costs).
  • An Azure DevOps organization. If you don't have one, you can create one for free.
  • An Azure DevOps Project with 'Project Administrator' permissions.
  • Source code stored in a Git repository (e.g., GitHub or Azure Repos). For this guide, we'll use GitHub.
  • Azure CLI installed and configured (version 2.x or later).
  • Azure DevOps CLI extension installed (`az extension add --name azure-devops`).
  • A GitHub account (if using GitHub for source control) with a Personal Access Token (PAT) for service connection, or administrative access to install the Azure Pipelines app.

Estimated Cost: Azure DevOps offers a generous free tier for private projects, including one parallel job that can run for up to 60 minutes, totaling up to 1,800 minutes per month. This is typically sufficient for many SMBs. However, to access this free grant, your Azure DevOps organization must have billing set up by linking a valid Azure subscription. You will only incur costs if you exceed the free tier limits or opt for self-hosted agents on Azure VMs.

Step 1: Prepare Your Azure DevOps Environment

Before creating your CI/CD pipeline, ensure your Azure DevOps organization and project are correctly set up and your CLI environment is ready. This foundational step ensures all subsequent commands execute smoothly within the right context.

# 1. Log in to Azure DevOps (interactive browser login)
az devops login

# 2. If you don't have an organization, create one (replace 'skycore-montreal' with your desired organization name)
az devops organization create --name skycore-montreal --location eastus

# 3. If you don't have a project within your organization, create one (replace 'SkyCoreWebApp' with your project name)
az devops project create --name SkyCoreWebApp --organization https://dev.azure.com/skycore-montreal/

# 4. Set default organization and project for subsequent CLI commands
az devops configure --defaults organization=https://dev.azure.com/skycore-montreal/ project=SkyCoreWebApp
  • az devops login: Initiates an interactive login process, opening your browser for authentication to Azure DevOps.
  • az devops organization create --name --location: Creates a new Azure DevOps organization. Choose a region close to your primary users for optimal performance (e.g., eastus for North America).
  • az devops project create --name --organization: Creates a new project within your specified organization. This project will house your repositories, pipelines, and other DevOps artifacts.
  • az devops configure --defaults organization=... project=...: This crucial command saves your preferred organization and project, so you don't have to specify them with every subsequent az devops command.

Portal alternative: Navigate to dev.azure.com, sign in, and follow the prompts to create an organization and a new project. Once created, you can access your project settings via the gear icon in the bottom left.

Run this to verify:

az devops project list --output table

Confirm that your newly created project (e.g., 'SkyCoreWebApp') is listed within your organization.

Step 2: Connect Your Source Code Repository (GitHub)

To enable Azure Pipelines to access and react to changes in your source code, you need to establish a secure connection to your Git repository. For SMBs, GitHub is a popular choice, offering robust version control and integration. We'll set up a GitHub service connection in Azure DevOps.

# 1. Create a GitHub Personal Access Token (PAT)
#    (Go to GitHub > Settings > Developer settings > Personal access tokens > Tokens (classic) > Generate new token)
#    Ensure the PAT has 'repo' scope access.

# 2. Create the Azure DevOps Service Endpoint for GitHub
az devops service-endpoint github create \
    --name "GitHub-SkyCore" \
    --organization "https://dev.azure.com/skycore-montreal/" \
    --project "SkyCoreWebApp" \
    --pat "YOUR_GITHUB_PAT_HERE"
  • --name "GitHub-SkyCore": A descriptive name for your service connection.
  • --organization and --project: Ensure these match your environment from Step 1.
  • --pat "YOUR_GITHUB_PAT_HERE": This is your GitHub Personal Access Token. Replace the placeholder with the actual PAT you generated in GitHub. It's recommended to store this PAT securely (e.g., in Azure Key Vault) and reference it programmatically for production setups, but for initial setup, direct use is shown.
Common pitfall: Ensure your GitHub PAT has the correct scopes. For CI/CD pipelines to read your code and potentially update status, the 'repo' scope is generally required. Insufficient permissions will lead to pipeline failures when trying to access the repository. Always create PATs with the principle of least privilege.

Portal alternative: In your Azure DevOps project, navigate to Project settings (bottom left) > Service connections > New service connection > Select GitHub. Choose 'Personal Access Token' for authentication, enter your PAT, and verify the connection.

Run this to verify:

az devops service-endpoint list --output table

Confirm that your 'GitHub-SkyCore' service endpoint is listed.

Step 3: Define Your CI/CD Pipeline with YAML

Azure Pipelines uses YAML files to define your CI/CD workflow. This approach, known as Infrastructure as Code, allows you to version control your pipeline definitions alongside your application code. For SMBs, YAML pipelines offer clarity, reusability, and maintainability. We'll create a basic CI pipeline for a .NET Core application, which is a common stack for many SMBs.

First, ensure you have an existing .NET Core application in a GitHub repository. For demonstration, you can fork Microsoft's sample: https://github.com/MicrosoftDocs/pipelines-dotnet-core. Let's assume your fork is at `https://github.com/your-github-user/pipelines-dotnet-core`.

# 1. Create the Azure Pipeline using the CLI
az pipelines create \
    --name "SkyCoreWebApp-CI" \
    --repository "your-github-user/pipelines-dotnet-core" \
    --branch "main" \
    --yaml-path "azure-pipelines.yml" \
    --repository-type "GitHub" \
    --service-connection "GitHub-SkyCore" \
    --folder "/"
  • --name "SkyCoreWebApp-CI": The name of your pipeline in Azure DevOps.
  • --repository "your-github-user/pipelines-dotnet-core": The GitHub repository in the format owner/repo. Replace your-github-user with your GitHub username.
  • --branch "main": The default branch for your repository where the YAML file will reside and changes will trigger the pipeline.
  • --yaml-path "azure-pipelines.yml": Specifies the name and path of the YAML file within your repository that defines the pipeline. The CLI will automatically commit a basic YAML file if one doesn't exist.
  • --repository-type "GitHub": Explicitly states the type of source repository.
  • --service-connection "GitHub-SkyCore": References the service connection created in Step 2.
  • --folder "/": Specifies the folder path in Azure Pipelines where this pipeline will be stored.

The CLI command above will attempt to create the `azure-pipelines.yml` file in the root of your repository and commit it. It will also suggest a template based on your repository's content. For a .NET Core project, it typically generates something similar to this:

# azure-pipelines.yml
# To get started with CI/CD, see https://aka.ms/yaml

trigger:
- main

pool:
  vmImage: 'ubuntu-latest'

variables:
  buildConfiguration: 'Release'

steps:
- task: DotNetCoreCLI@2
  displayName: 'Restore .NET Dependencies'
  inputs:
    command: 'restore'
    projects: '**/*.csproj'

- task: DotNetCoreCLI@2
  displayName: 'Build .NET Project'
  inputs:
    command: 'build'
    projects: '**/*.csproj'
    arguments: '--configuration $(buildConfiguration)'

- task: DotNetCoreCLI@2
  displayName: 'Run .NET Tests'
  inputs:
    command: 'test'
    projects: '**/*.csproj'
    arguments: '--configuration $(buildConfiguration)'

- task: DotNetCoreCLI@2
  displayName: 'Publish .NET Artifact'
  inputs:
    command: 'publish'
    projects: '**/*.csproj'
    arguments: '--configuration $(buildConfiguration) --output $(Build.ArtifactStagingDirectory)'
    zipAfterPublish: true

- task: PublishBuildArtifacts@1
  displayName: 'Publish Build Artifacts'
  inputs:
    pathToPublish: '$(Build.ArtifactStagingDirectory)'
    artifactName: 'drop'
  • trigger: - main: This specifies that the pipeline will automatically run whenever changes are pushed to the main branch.
  • pool: vmImage: 'ubuntu-latest': This tells Azure Pipelines to use a Microsoft-hosted agent running Ubuntu. For SMBs, Microsoft-hosted agents are the recommended option as they require no infrastructure management, are pre-configured with common tools, and scale automatically.
  • variables: buildConfiguration: 'Release': Defines a reusable variable.
  • tasks:: These are the actual operations. The DotNetCoreCLI@2 task is a versatile task for .NET Core operations (restore, build, test, publish). PublishBuildArtifacts@1 makes the compiled application (or other output) available for subsequent stages (like deployment).
Pro tip: For production pipelines, consider adding security scanning tasks (e.g., WhiteSource Bolt, SonarCloud) or code quality checks directly within your CI process. This helps catch vulnerabilities and maintain code standards early, aligning with security hardening best practices for SMBs.

Portal alternative: In your Azure DevOps project, go to Pipelines > New pipeline. Follow the wizard, selecting GitHub, your repository, and then choosing the suggested template (e.g., ASP.NET Core) which will generate a similar YAML file. Review and click 'Save and run'.

Run this to verify:

az pipelines show --name "SkyCoreWebApp-CI" --query "name"

This command should return the name of your pipeline, confirming its creation. You can also check your GitHub repository for the `azure-pipelines.yml` file.

Step 4: Trigger and Monitor Your First Pipeline Run

With your pipeline defined, it's time to put it to the test. A new pipeline created via the CLI (or 'Save and run' in the portal) often triggers an initial run automatically. You can also manually trigger a run or make a small code change to your main branch to see the trigger in action.

# 1. Queue a new run for your pipeline (if not already triggered)
az pipelines run queue --name "SkyCoreWebApp-CI" --branch "main"

# 2. List recent runs for your pipeline
az pipelines runs list --name "SkyCoreWebApp-CI" --query "[].{id:id, status:status, result:result, sourceBranch:sourceBranch, triggeredBy:triggeredBy.displayName}" --output table

# 3. View details of a specific run (replace <RUN_ID> with an ID from the list command)
az pipelines runs show --id <RUN_ID> --name "SkyCoreWebApp-CI"
  • az pipelines run queue: Manually starts a new pipeline run for the specified pipeline and branch. This is useful for testing or re-running failed builds.
  • az pipelines runs list: Provides a summary of recent pipeline runs, including their status (e.g., 'running', 'completed'), result (e.g., 'succeeded', 'failed'), and who triggered them.
  • az pipelines runs show --id: Fetches detailed information about a specific pipeline run, including all jobs and steps.
Common pitfall: If your pipeline fails, meticulously review the logs in the Azure DevOps portal. The logs provide detailed output for each step, which is crucial for identifying compilation errors, failing tests, or misconfigurations. Start troubleshooting from the first failed task.

Portal alternative: In your Azure DevOps project, navigate to Pipelines > Select your pipeline ('SkyCoreWebApp-CI'). You'll see a list of runs. Click on a specific run to view its stages, jobs, and detailed logs. You can also click 'Run pipeline' to manually trigger a new run.

Run this to verify:

az pipelines runs list --name "SkyCoreWebApp-CI" --top 1 --query "[0].status"

This should show the status of your latest pipeline run. Ideally, it should be 'completed' with a 'succeeded' result.

Step 5: Review Pipeline Artifacts and Deployment Considerations

A successful CI pipeline not only builds and tests your code but also produces artifacts – the deployable outputs of your build. These artifacts are the foundation for your Continuous Delivery (CD) process. In our example YAML, the PublishBuildArtifacts@1 task created a 'drop' artifact containing your published .NET Core application.

# 1. List artifacts from a specific pipeline run (replace <RUN_ID>)
az pipelines runs artifact list --run-id <RUN_ID> --output table

# 2. Download an artifact (replace <RUN_ID> and <ARTIFACT_NAME>)
az pipelines runs artifact download --run-id <RUN_ID> --artifact-name "drop" --path ".\artifacts"
  • az pipelines runs artifact list: Displays a list of all artifacts published by a specific pipeline run.
  • az pipelines runs artifact download: Downloads a specific artifact from a run to your local machine. This is useful for manual verification or transferring artifacts to other systems.
Pro tip: To extend this into a full CD pipeline, you would add a 'stage' for deployment in your `azure-pipelines.yml`. This stage would consume the 'drop' artifact and deploy it to a target environment (e.g., Azure App Service, Virtual Machine, Kubernetes). Azure DevOps Environments can help manage deployment targets and approvals for various stages (Dev, Test, Production).

Portal alternative: After a pipeline run completes successfully, navigate to the pipeline run details in the Azure DevOps portal. Click on the 'Summary' tab, and you'll see an 'Artifacts' section. Click on 'drop' to browse the contents or download the artifact directly.

Run this to verify:

# Verify downloaded artifact contents (PowerShell example)
# Make sure you've downloaded the artifact using the CLI command above first
Get-ChildItem -Path ".\artifacts\drop" -Recurse

This command will list the files within your downloaded artifact, confirming that your application was successfully packaged.
